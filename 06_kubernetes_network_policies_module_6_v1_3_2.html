Network Policies

Learn how Kubernetes decides which pod connections are allowed, how selectors define trust boundaries, why CNI enforcement matters, and how to move from an open namespace to a deliberate least‑privilege policy set without breaking DNS or application traffic.

How to study this module

learner path
1 · Understand

Build the mental model

Start with the packet path. Ask: Who is the source? Who is the destination? Which direction is being filtered?

2 · Read

Translate YAML into English

Do not memorize YAML. Read each policy as a sentence: “Select these pods, isolate this direction, allow these peers, on these ports.”

3 · Prove

Four questions before reading any NetworkPolicy

Q1 — Which pods does it select?

Read spec.podSelector first. If no running pods match, valid YAML can still affect nothing.

Q2 — Which direction is isolated?

policyTypes tells you whether ingress, egress, or both are controlled.

Q3 — Who or what is allowed?

Read from, to, selectors and ipBlock.

Q4 — Which destination port?

Port 443 means L4 destination port 443. It does not mean “trusted HTTPS application.”

Important distinction: Ingress objects/controllers are application-routing components. Kubernetes NetworkPolicy is an allow-list security control normally enforced by the CNI/network plugin. They solve related but different problems.

6.1 NetworkPolicy Fundamentals

core mental model
Prerequisite assumed here: you already understand Pods, namespaces, labels, Services, ClusterIP and basic CNI purpose. If “CNI” is only a familiar acronym, read the CNI gate below before running any lab.

Deep dive: from open to isolated

Separate pod existence from pod isolation state. A pod can be healthy and reachable, then become isolated for only one traffic direction when a policy starts selecting it.

State A
No policy selects pod
non-isolated
State B
Selected for ingress
ingress isolated
State C
Selected for ingress + egress
both isolated

Isolation does not mean “deny everything.” It means traffic in that direction must now be allowed by at least one applicable policy.

Read a policy like a sentence

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-api
  namespace: shop
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: web
    ports:
    - protocol: TCP
      port: 8080
English translation

“In namespace shop, select app=api pods. Isolate them for ingress. Permit app=web pods in the same namespace to reach TCP/8080.”

What it does not say

It does not control API egress, does not allow web pods from every namespace, and does not permit TCP/8081.

The one sentence definition

A NetworkPolicy selects a set of pods in one namespace and describes the network traffic those selected pods are allowed to receive, send, or both.

Selection

Which pods?

spec.podSelector selects the pods to which the policy applies. An empty selector {} means every pod in that policy’s namespace.

Direction

Ingress / Egress

policyTypes determines whether the selected pods are isolated for incoming traffic, outgoing traffic, or both.

Allowance

Who / where / port?

Rules allow selected peers and ports. NetworkPolicy is allow-list oriented: after isolation begins, unmatched traffic is denied.

Default allow is the starting state

Without an applicable NetworkPolicy, pods are non-isolated in that direction. That is why merely creating a namespace does not create a network security boundary.

The CNI enforcement gate

A policy object can exist and still do nothing. Kubernetes stores the NetworkPolicy API object; a network plugin that supports NetworkPolicy must enforce it. Never validate the feature by checking only kubectl get networkpolicy — validate with a traffic test.
# Identify common CNI components (names vary by distribution)
kubectl get pods -n kube-system -o wide

# See policy objects
kubectl get networkpolicy -A

# Do NOT stop here. Enforcement must be proved with an allow/deny test.
Implementation detail: what “isolation” means

Ingress and egress isolation are independent. A pod becomes isolated for a direction when at least one policy selects that pod and applies to that direction. Once isolated, traffic in that direction must match an allow rule from at least one applicable policy.

Reply traffic for an allowed connection is normally implicitly allowed; NetworkPolicy is concerned with permitted connection establishment rather than forcing you to author symmetric return-path rules for every flow.

6.2 Ingress & Egress Rules

two-sided connection

Ingress is evaluated at the destination pod. Egress is evaluated at the source pod. A pod-to-pod connection succeeds only when both sides permit it, if each side is isolated for that direction.

Deep dive: one connection, two policy decisions

Example: frontend → api:8080. If frontend is egress-isolated, its egress must allow the API. If API is ingress-isolated, its ingress must allow the frontend. When both sides are isolated, both decisions must permit the flow.

Additive behavior: there is no policy priority

Standard NetworkPolicy does not behave like a top-to-bottom firewall chain. If multiple policies select a pod, their allowed flows are combined.

PolicyAllows
Afrontend → api:8080
Bmonitoring → api:9090
Effective resultBoth flows are allowed
Security consequence: a broad allow cannot be “overridden” by a later stricter standard NetworkPolicy.
Source pod
Is it egress-isolated?
Allowed destination + destination port?
→
Destination pod
Is it ingress-isolated?
Allowed source + destination port?
Ingress: the policy selects destination pods. from describes permitted sources; ports describes destination ports on the selected pods.
Egress: the policy selects source pods. to describes permitted destinations; ports describes destination ports.
Combined: there is no “policy priority.” Applicable policies are unioned. One policy can allow DNS while another allows an API destination; both allowances coexist.

Port and protocol matching

FieldMeaningPractical note
protocolTCP, UDP or SCTPDefaults to TCP when omitted.
portDestination port number or supported named portBe precise; allowing port 443 does not mean “HTTPS identity,” only L4 destination port 443.
endPortInclusive end of a numeric port rangeUseful for controlled ranges; support depends on plugin implementation.

Minimal ingress allow policy

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-from-frontend
  namespace: shop
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080

Read it as: “For app=api pods in namespace shop, ingress is restricted; permit TCP/8080 from app=frontend pods in the same namespace.”

Common YAML trap: two peer selector entries mean OR; namespaceSelector and podSelector in the same peer entry mean AND. The indentation changes the security meaning.

6.3 Label Selectors

identity by metadata

Selectors are the core policy identity mechanism. NetworkPolicy does not target a Deployment object; it targets pods whose labels match at evaluation time.

Deep dive: selector scope and AND/OR logic

Most learner mistakes happen here because visually similar YAML can represent different trust relationships.

ShapeMeaning
podSelector onlyMatching pods in the policy's own namespace
namespaceSelector onlyAll pods in matching namespaces
namespaceSelector + podSelector in one peerMatching pods inside matching namespaces — AND
Two separate peer list entriesEither peer can match — OR
Production insight: once labels authorize network access, label modification is security-sensitive. RBAC and admission controls become part of the network trust model.

matchLabels vs matchExpressions

Use matchLabels for exact identities. Use matchExpressions when membership in a set is the better model.

podSelector:
  matchExpressions:
  - key: environment
    operator: In
    values: ["production", "staging"]
  - key: network-access
    operator: Exists
matchLabels

Exact equality

Best for straightforward identities such as app: api, tier: backend, or security-zone: restricted.

matchExpressions

Set-based matching

Use operators such as In, NotIn, Exists and DoesNotExist when one exact label pair is not expressive enough.

podSelector:
  matchExpressions:
  - key: role
    operator: In
    values: ["frontend", "gateway"]
  - key: exposed
    operator: Exists

Pod selector scope

A peer podSelector by itself refers to pods in the same namespace as the NetworkPolicy. To select pods in other namespaces, add a namespaceSelector.

from:
- podSelector:
    matchLabels:
      app: frontend
from:
- namespaceSelector:
    matchLabels:
      access-to-shop: "true"
from:
- namespaceSelector:
    matchLabels:
      access-to-shop: "true"
  podSelector:
    matchLabels:
      app: frontend
Built-in namespace name label

Kubernetes namespaces normally carry the immutable label kubernetes.io/metadata.name. This is convenient when a policy must allow a specifically named namespace without requiring your own business label first.

6.4 IPBlock Rules

use deliberately

ipBlock matches IP CIDR ranges. It is most predictable for cluster-external networks such as a database subnet, proxy, legacy endpoint or controlled egress destination.

Deep dive: where IPBlock fits

ipBlock is best when the peer is naturally represented as a network rather than Kubernetes workload identity.

Good fit

External subnet

Corporate proxy, external API range, on-prem database subnet or appliance.

Poor fit

Dynamic Pods

Pod IPs change. Prefer label selectors for Kubernetes workloads.

Caution

Service VIP

NAT and Service implementation can change which address the policy engine sees.

except: allow a parent CIDR but carve out one or more contained ranges that must remain excluded.
egress:
- to:
  - ipBlock:
      cidr: 10.40.0.0/16
      except:
      - 10.40.7.0/24
  ports:
  - protocol: TCP
    port: 443

This allows TCP/443 to 10.40.0.0/16 except addresses inside 10.40.7.0/24.

NAT caveat: NetworkPolicy processing can see different source/destination addresses depending on CNI, Service implementation, cloud networking and where address translation occurs. Do not assume an ipBlock always sees the original client IP or Service IP.

Hybrid selector + IPBlock scenario

You can use separate rules to allow internal application peers and an external CIDR. Treat these as two explicit trust relationships, not one broad exception.

egress:
# Internal: selected pods in a selected namespace
- to:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: payments
    podSelector:
      matchLabels:
        app: ledger
  ports:
  - port: 8443
    protocol: TCP

# External: managed API subnet
- to:
  - ipBlock:
      cidr: 203.0.113.0/24
  ports:
  - port: 443
    protocol: TCP

6.5 Namespaced Policies

scope matters

A NetworkPolicy is namespaced. Its spec.podSelector can select only pods in the policy’s own namespace. Peer selectors can authorize traffic from/to other namespaces.

Deep dive: namespaces as trust zones

Namespaces are useful organizational boundaries, but they are not automatically network-isolated. NetworkPolicy turns namespace and pod labels into enforceable traffic relationships.

Pattern A

Web → API

Permit only frontend pods from the web namespace to selected API pods.

Pattern B

Monitoring

Permit a controlled monitoring namespace to scrape designated metrics ports.

Pattern C

Platform services

Allow DNS or platform control traffic intentionally instead of opening the whole namespace.

Cross-namespace communication pattern

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-from-web
  namespace: api
spec:
  podSelector:
    matchLabels:
      app: orders
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: web
      podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080

Namespace isolation patterns

PatternUseRisk to watch
Namespace default denySecurity baseline for all pods in a namespaceBreaks DNS or monitoring if egress/ingress exceptions are omitted.
Namespace label trustAuthorize whole namespaces by controlled labelsWho can modify namespace labels becomes a security concern.
Namespace + pod labelStrongest native peer scopingRequires label governance in both namespaces.

6.6 Default Deny / Allow Patterns

progressive lockdown

A robust rollout normally starts by observing required flows, then introducing default isolation and narrowly restoring legitimate traffic.

Step 1

Baseline

Inventory application flows: clients, server ports, DNS, telemetry, external dependencies, probes and administrative paths.

Step 2

Default deny

Apply namespace-wide isolation in a controlled environment. Expect breakage if dependencies were missed.

Step 3

Restore minimally

Add targeted policies. Because policies are additive, split rules by purpose when that improves ownership and review.

Progressive lockdown: safer than denying everything at once

  1. Observe actual application dependencies.
  2. Document every required source → destination → protocol → port flow.
  3. Prove baseline health before changing policy.
  4. Deny ingress by default and restore required inbound flows.
  5. Deny egress role-by-role rather than isolating the entire application at once.
  6. Restore DNS and external dependencies deliberately.
  7. Keep negative tests so unintended access stays blocked.

Why DNS is often the first failure

Applications usually connect by hostname. After egress isolation, DNS itself can be blocked before the application ever attempts its intended TCP connection.

Debug order: after egress lockdown, test name resolution first. If DNS fails, application errors can look misleading or unrelated to NetworkPolicy.

Default deny ingress

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: shop
spec:
  podSelector: {}
  policyTypes:
  - Ingress

Default deny egress

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: shop
spec:
  podSelector: {}
  policyTypes:
  - Egress
DNS is the classic egress-lockdown failure. If egress is denied, applications may report “host not found,” timeouts, or unrelated-looking failures until DNS traffic to the cluster DNS path is explicitly allowed. Validate the actual DNS pods/service and your CNI semantics instead of copying a cluster-specific rule blindly.

Allow all — explicit escape hatch

An empty rule item such as ingress: - {} or egress: - {} explicitly allows all traffic in that direction for selected pods. Because policies are additive, an allow-all policy cannot be “overridden” by another stricter NetworkPolicy for the same direction.

Prerequisite Lab — Migrate Flannel → Cilium

cluster-changing
This changes cluster networking. Run it only on the dedicated training cluster or during an approved maintenance window. Do not delete Flannel first. The safer migration model is: install Cilium in secondary mode → migrate nodes one by one → make Cilium primary → remove Flannel last.
Official migration constraints: live migration requires a new distinct Cilium pod CIDR, cluster-pool IPAM, and a distinct overlay protocol or port. Cilium documents this migration path for existing plugins that use the Linux routing stack such as Flannel. It is not the place to simultaneously change IP families or introduce BGP routing. During mixed-CNI operation, Cilium policy enforcement must remain disabled.

Why the order matters

M3 — Choose a migration CIDR distinct from Flannel

This module assumes the common Flannel pod network 10.244.0.0/16. During controlled migration, use a different unused pool for Cilium, for example 10.245.0.0/16.

# Verify 10.245.0.0/16 is NOT already used in your environment.
kubectl get nodes -o custom-columns=NAME:.metadata.name,PODCIDR:.spec.podCIDR
ip route | grep 10.245 || true

export CILIUM_POD_CIDR=10.245.0.0/16
echo "$CILIUM_POD_CIDR"
Do not blindly use 10.245.0.0/16. It must not overlap node networks, Service CIDRs, VPNs, datacenter routes, existing pod networks, or other routed networks reachable from the cluster.

M4 — Install Cilium 1.20.2 in migration/secondary mode

Flannel commonly uses VXLAN UDP/8472. During coexistence this lab gives Cilium a different VXLAN port, 8473.

Node firewall requirement: allow UDP/8473 between all Kubernetes nodes before installing Cilium. Because this module keeps tunnelPort: 8473 in the final Helm values, UDP/8473 remains the Cilium VXLAN port after migration unless you deliberately schedule a later change. Do not close it after removing Flannel.
cat > values-migration.yaml <<'EOF'
operator:
  unmanagedPodWatcher:
    restart: false

routingMode: tunnel
tunnelProtocol: vxlan
tunnelPort: 8473

cni:
  customConf: true
  uninstall: false

ipam:
  mode: cluster-pool
  operator:
    clusterPoolIPv4PodCIDRList:
      - 10.245.0.0/16

policyEnforcementMode: "never"

bpf:
  hostLegacyRouting: true
EOF

# Let the CLI auto-detect additional values, then review them.
cilium install 1.20.2 \
  --values values-migration.yaml \
  --dry-run-helm-values > values-initial.yaml

less values-initial.yaml

helm repo add cilium https://helm.cilium.io/
helm repo update
helm install cilium cilium/cilium \
  --version 1.20.2 \
  --namespace kube-system \
  --values values-initial.yaml

cilium status --wait
Expected at this point: Cilium is healthy enough to establish its overlay, but existing pods are still using Flannel. Policy enforcement stays disabled during mixed-CNI migration.

M6 — Migrate one worker at a time

Start with a worker, not the control plane. On your three-node training cluster, use the order w1 → w2 → master.

Execution-location rule: all kubectl and cilium commands in M6 must run from the ADMIN / CONTROL-PLANE host where cluster access already works. Do not run them from w1 or w2 unless those workers were intentionally configured with a valid kubeconfig.
ADMIN / CONTROL-PLANE

Cluster operations

Run kubectl, cilium, cordon, drain, labels, pod deletion, status checks and validation here.

TARGET WORKER

Node-local operations

Run only host commands such as inspecting /etc/cni/net.d/, checking kubelet logs and rebooting the node.

M6A — ADMIN / CONTROL-PLANE: verify kubeconfig first

# Run on the admin/control-plane host.
kubectl cluster-info
kubectl get nodes

# If kubectl tries http://localhost:8080, STOP.
# This host does not have a usable kubeconfig for the cluster.
echo "${KUBECONFIG:-$HOME/.kube/config}"

M6B — ADMIN / CONTROL-PLANE: cordon, drain, label and restart Cilium

# Run on the admin/control-plane host.
export NODE=w1

kubectl cordon "$NODE"

# Review PodDisruptionBudget or unmanaged-pod errors.
# Do not add --force blindly.
kubectl drain "$NODE" \
  --ignore-daemonsets \
  --delete-emptydir-data

kubectl label node "$NODE" --overwrite \
  io.cilium.migration/cilium-default=true

# Restart only the Cilium pod scheduled on this node.
kubectl -n kube-system delete pod \
  --field-selector spec.nodeName="$NODE" \
  -l k8s-app=cilium

# Confirm a replacement Cilium pod appears on the target node.
kubectl -n kube-system get pods -l k8s-app=cilium -o wide
cilium status --wait

M6C — TARGET WORKER (w1): verify CNI files, then reboot

# Run locally on w1, using SSH/console/node-management access.
sudo ls -la /etc/cni/net.d/

# During migration you should now see Cilium's generated CNI config,
# typically including:
#   05-cilium.conflist
#
# Keep the existing Flannel config during controlled migration.
# Do NOT manually delete CNI files here.

sudo journalctl -u kubelet -n 50 --no-pager

M6D — ADMIN / CONTROL-PLANE: validate the migrated worker

# Run on the admin/control-plane host.
export NODE=w1

kubectl get node "$NODE" -o wide
kubectl wait --for=condition=Ready "node/$NODE" --timeout=180s

# Confirm Cilium is Running on w1.
kubectl -n kube-system get pods -l k8s-app=cilium -o wide

# Run a disposable test pod specifically on the migrated node.
kubectl -n kube-system run --attach --rm --restart=Never verify-cilium \
  --overrides='{"spec":{"nodeName":"'"$NODE"'","tolerations":[{"operator":"Exists"}]}}' \
  --image=ghcr.io/nicolaka/netshoot:v0.13 \
  -- /bin/bash -c 'ip -br addr; curl -s -k https://$KUBERNETES_SERVICE_HOST/healthz; echo'

# PASS criteria:
# 1. test pod gets an IP from the Cilium migration pool
#    (10.245.0.0/16 in this module);
# 2. Kubernetes API /healthz succeeds;
# 3. node remains Ready;
# 4. Cilium on the node is healthy.

kubectl uncordon "$NODE"

If you accidentally run kubectl on w1

Typical error: The connection to the server localhost:8080 was refused. This means the worker has no usable kubeconfig and kubectl is not connected to the Kubernetes API. Return to the admin/control-plane host and continue M6 there. Do not copy cluster-admin credentials to workers merely to make this lab work.

Repeat M6B → M6D for w2. Migrate the control-plane node last. If the control-plane node contains workloads that cannot be drained normally, inspect those workloads and any PodDisruptionBudgets before proceeding.

Use the removal method that matches how Flannel was installed.

helm list -A | grep -i flannel

What if the migration breaks?

Stop after the affected node. Do not migrate the remaining nodes. Inspect cilium status, the Cilium pod on that node, kubelet events and the files under /etc/cni/net.d/. Because migration is node-by-node, healthy unmigrated nodes remain a useful comparison point.

Policy Design Worksheet

production habit

Before writing YAML, express the requirement as a traffic contract. This prevents “policy by trial and error.”

SourceDestinationProtocol / PortReasonExpected result
app=frontendapp=apiTCP/8080Application requestALLOW
app=strangerapp=apiTCP/8080No business requirementDENY
app=apicluster DNSUDP/TCP 53Name resolutionALLOW
Operational rule: Every ALLOW row should have a neighboring DENY test. A policy that only proves intended traffic works does not prove unwanted traffic is blocked.

Five-minute review checklist

1. Selector

Does podSelector match the pods you think it matches?

2. Direction

Ingress, egress, or both?

3. Peer scope

Same namespace, selected namespace, or CIDR?

4. Port

Destination protocol and port correct?

5. Additive policies

Could another policy already allow the flow?

6. Platform dependency

DNS, monitoring, service mesh, admission or control-plane traffic?

Standard NetworkPolicy boundaries

Standard Kubernetes NetworkPolicy is primarily an L3/L4 control. It does not natively express HTTP paths, users, JWT claims, TLS identities or “deny this specific rule after another allow.” If a course later introduces Cilium, Calico or service-mesh policy, keep those extensions conceptually separate from the standard API taught here.

Ingress isolation + selective allow
Learn destination-side policy logic
# Allow only app=client to reach app=server on TCP/80
cat <<'EOF' | kubectl apply -f -

kind: NetworkPolicy
metadata:
  name: server-from-client
  namespace: np-lab
spec:
  podSelector:
    matchLabels:
      app: server
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: client
    ports:
    - protocol: TCP
      port: 80
EOF

# Existing client should succeed again
kubectl -n "$NPNS" exec client -- wget -qO- --timeout=3 http://server

# Untrusted client should fail
kubectl -n "$NPNS" run stranger --image=busybox:1.36 --labels=app=stranger \

Expected: client succeeds; stranger fails. The original deny policy remains present, but the new allow policy adds a permitted path.

Egress lockdown, DNS recovery and application recovery
Prove each dependency separately

This lab avoids hiding several concepts behind one test. First deny all egress from app=client. Then restore DNS. Finally restore access to app=server.

Step 3A — Capture the server Pod IP and DNS Pod IP

export SERVER_POD_IP=$(kubectl -n "$NPNS" get pod server -o jsonpath='{.status.podIP}')
echo "server pod IP: $SERVER_POD_IP"

# Discover likely cluster DNS pods.
kubectl -n kube-system get pods --show-labels | grep -Ei 'coredns|kube-dns'

# For a typical kubeadm/CoreDNS cluster:
export DNS_POD_IP=$(kubectl -n kube-system get pods -l k8s-app=kube-dns \
  -o jsonpath='{range .items[0:1]}{.status.podIP}{end}')
echo "dns pod IP: $DNS_POD_IP"

# If empty, STOP this step, inspect the labels above, and substitute
# the DNS selector used by your distribution before continuing.

Step 3B — Prove baseline egress works

# Direct application traffic
kubectl -n "$NPNS" exec client -- wget -qO- --timeout=3 "http://${SERVER_POD_IP}"

# Direct DNS query to the discovered DNS pod
kubectl -n "$NPNS" exec client -- nslookup server.np-lab.svc.cluster.local "$DNS_POD_IP"

Step 3C — Deny all egress from only app=client

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-deny-all-egress
  namespace: np-lab
spec:
  podSelector:
    matchLabels:
      app: client
  policyTypes:
  - Egress
EOF

# Both tests should now fail.
kubectl -n "$NPNS" exec client -- wget -qO- --timeout=3 "http://${SERVER_POD_IP}"
echo "HTTP exit=$?"

kubectl -n "$NPNS" exec client -- nslookup server.np-lab.svc.cluster.local "$DNS_POD_IP"
echo "DNS exit=$?"

Step 3D — Restore DNS only

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-allow-dns
  namespace: np-lab
spec:
  podSelector:
    matchLabels:
      app: client
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
EOF

# DNS should recover.
kubectl -n "$NPNS" exec client -- nslookup server.np-lab.svc.cluster.local "$DNS_POD_IP"

# HTTP should STILL fail because only DNS was restored.
kubectl -n "$NPNS" exec client -- wget -qO- --timeout=3 "http://${SERVER_POD_IP}"
echo "HTTP exit=$?"

Step 3E — Restore application egress

cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: client-allow-server
  namespace: np-lab
spec:
  podSelector:
    matchLabels:
      app: client
  policyTypes:
  - Egress
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: server
    ports:
    - protocol: TCP
      port: 80
EOF

# Direct Pod traffic should now work again.
kubectl -n "$NPNS" exec client -- wget -qO- --timeout=3 "http://${SERVER_POD_IP}"
What this proves: NetworkPolicies are additive. The deny-all policy keeps the client egress-isolated, while separate allow policies independently restore DNS and application traffic.
DNS portability: k8s-app=kube-dns is common on kubeadm/CoreDNS clusters but is not universal. The lab deliberately makes trainees inspect DNS labels first. If your distribution uses different labels, change only the DNS podSelector.
4
Progressive lockdown exercise
Turn an open namespace into least privilege
  1. Record required flows for every pod role.
  2. Apply namespace-wide default deny ingress.
  3. Restore only required ingress.
  4. Apply default deny egress to one role first.
  5. Restore DNS and required destinations.
  6. Repeat role by role.
  7. Keep a positive and negative test for each intended trust relationship.
Success criterion: a policy rollout is not complete when desired traffic works. It is complete when desired traffic works and representative undesired traffic is demonstrably blocked.

Common Misconceptions

exam + production
MisconceptionCorrect model
“A namespace is network-isolated by default.”No. Pods are normally non-isolated until NetworkPolicy selects them for a direction.
“The last policy wins.”No. Standard NetworkPolicies are additive.
“A deny-all policy overrides an allow policy.”No. Once isolated, any applicable allow rule can permit the matching traffic.
“Ingress policy controls Kubernetes Ingress objects.”No. NetworkPolicy ingress means traffic entering selected pods.
“A Service is a NetworkPolicy identity.”Policies fundamentally reason about selected pods, namespaces and IP blocks; Service/NAT paths can introduce implementation details.
“If kubectl accepts the object, enforcement works.”No. Only a traffic test proves enforcement.

Implementation Caveats Worth Remembering

Host traffic

Traffic involving the pod’s node and hostNetwork workloads can have implementation-specific behavior. Treat it as a CNI-specific validation point.

L7 is outside standard NetworkPolicy

Standard NetworkPolicy understands addresses, peers, protocols and ports — not HTTP paths, JWT claims or application identities. Some CNIs expose additional non-standard policy APIs for L7.

Services are not policy identities

Write rules around pod/namespace identities and observable destination behavior. A Service VIP may be rewritten before or after enforcement depending on implementation.

Labels are security data

If authorization depends on a label, control who can modify that label. RBAC/admission policy becomes part of the trust model.
