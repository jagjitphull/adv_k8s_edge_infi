7.0 · Troubleshooting mindset

Diagnose in layers, not by guessing

Assumed knowledge: you should already know Pods, Deployments, Services, labels/selectors, namespaces, resource requests/limits, and the basic idea of PersistentVolumeClaims. If any of those terms are unfamiliar, review them before the corresponding section.
1 · Observe

Capture current state: Pod phase, node assignment, restart count, readiness, PVC state, Service endpoints.

2 · Read Events

Events often expose scheduler rejection, mount failures, image pull errors, probe failures, or node pressure.

3 · Narrow the layer

Control plane? scheduler? kubelet? runtime? CNI? DNS? Service? policy? CSI/storage?

Start every Pod incident here
kubectl get pod -A -o wide
kubectl describe pod <pod> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
Cluster-level sanity check
kubectl get nodes -o wide
kubectl get --raw='/readyz?verbose'
kubectl get events -A --sort-by=.lastTimestamp
Best practice: collect evidence before deleting or restarting the Pod. A restart can remove the most useful evidence and turn a deterministic problem into an intermittent one.
Field Manual · Pod & container state decoder

Pod phase is not the same as container waiting reason

A Pod can have phase Running while a container is repeatedly failing. The STATUS column is often a human-friendly summary derived from container state.

Crash / restart diagnosis
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> --all-containers=true
kubectl logs <pod> -n <ns> --all-containers=true --previous
kubectl get pod <pod> -n <ns> -o jsonpath='{range .status.containerStatuses[*]}{.name}{" reason="}{.state.waiting.reason}{" last="}{.lastState.terminated.reason}{" exit="}{.lastState.terminated.exitCode}{" restarts="}{.restartCount}{"\n"}{end}'
Image/config diagnosis
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.containers[*].image}{"\n"}'
kubectl get pod <pod> -n <ns> -o jsonpath='{.spec.imagePullSecrets[*].name}{"\n"}'
kubectl get events -n <ns> --sort-by=.lastTimestamp
Good interpretation: “Container exits with code 1; previous logs show a missing configuration file. This is an application/configuration failure, not a scheduler problem.”
Poor interpretation: “Pod is CrashLoopBackOff, therefore Kubernetes is broken.” The status describes a symptom, not the root cause.
7.1 · Debugging Pending Pods

“Pending” is a phase, not a root cause

A Pending Pod has been accepted by the API server but one or more containers are not yet running. Often it has not been scheduled, but a Pod can also remain Pending while images are being prepared or other startup prerequisites are unresolved. The scheduler’s Events are the fastest way to distinguish these situations.

  1. Check whether NODE is empty. If empty, think scheduler. If a node is assigned, shift focus toward kubelet/runtime/image/storage startup.
  2. Read the Events section of kubectl describe pod. Look for FailedScheduling, FailedMount, FailedAttachVolume, or image errors.
  3. For scheduling failures, compare Pod constraints against actual node labels, taints, allocatable CPU/memory, affinity, topology, and volume constraints.
  4. Change only the constraint you have proven is responsible, then verify scheduling and startup separately.

7.2 · Networking Issue Diagnosis

Test the path in layers

Assumed knowledge: Services, selectors, EndpointSlices/endpoints, DNS names, CNI basics, and NetworkPolicy concepts. If NetworkPolicy was not yet covered in your sequence, treat policy checks below as an advanced dependency.

A network symptom such as “connection refused” or “timeout” is not enough to identify the failing component. Test from the same network context as the application and progressively narrow the path: DNS → Service VIP/name → endpoints → Pod IP → application port → policy/CNI/node path.

DNS succeeds, Service fails

Inspect Service ports/targetPorts and EndpointSlices. If there are no ready endpoints, inspect selectors and Pod readiness.

Pod IP works, Service IP fails

Focus on Service plumbing and node networking: kube-proxy replacement, eBPF dataplane, service rules, or the CNI implementation.

Service works in one namespace only

Check NetworkPolicy, namespace selectors, DNS search suffix assumptions, and whether the caller uses the correct FQDN.

Timeout vs refused

Refused often means the destination is reachable but nothing accepts that port. Timeout more often suggests filtering, routing, policy, or an unreachable endpoint.

Create a temporary troubleshooting Pod
kubectl run net-debug \
  --image=registry.k8s.io/e2e-test-images/agnhost:2.53 \
  --restart=Never -it --rm -- sh
Service and endpoint checks
NS=<namespace>
SVC=<service>

kubectl get svc "$SVC" -n "$NS" -o wide
kubectl describe svc "$SVC" -n "$NS"
kubectl get endpointslices -n "$NS" \
  -l kubernetes.io/service-name="$SVC" -o wide
kubectl get pods -n "$NS" --show-labels
DNS checks from inside a Pod
nslookup <service>
nslookup <service>.<namespace>.svc.cluster.local
cat /etc/resolv.conf
When the application image has no shell or tools
kubectl debug -it pod/<pod> -n <namespace> \
  --image=busybox:1.36 --target=<container>

7.3 · Storage Mount Failures

Separate binding, attachment, and mount

Assumed knowledge: PersistentVolume, PersistentVolumeClaim, StorageClass, access modes, CSI, and dynamic provisioning. If CSI has not been covered, note that provisioning/attach/mount failures may involve controller-side and node-side CSI components.
Binding

PVC must match or trigger provisioning of a suitable PV. Evidence lives on PVC, PV, StorageClass, and provisioner Events.

Attachment

For attachable storage, the volume must be attached to the selected node. Cloud/storage API and CSI controller failures appear here.

Mount

Kubelet/CSI node plugin must mount the volume into the Pod. Filesystem, permissions, missing helper, path, or node plugin issues surface here.

volume node affinity conflictSelected node conflicts with volume topologyPV nodeAffinity, StorageClass topology, scheduler placement
Multi-Attach errorAccess mode / attach semantics conflictExisting attachment, workload replicas, storage capabilities

Why WaitForFirstConsumer can prevent topology mistakes With topology-constrained storage, delaying binding/provisioning until the scheduler has workload placement information helps align the volume with a node/zone where the Pod can actually run. This avoids provisioning a volume in a topology that later conflicts with scheduling.
HostPath warning hostPath is node-local and couples the Pod to a node’s filesystem. It is useful for controlled labs and some node-level workloads, but should not be treated as a portable persistent-storage design for general applications.
7.4 · Scheduling Conflicts

Think in filters: which requirement rejects every node?

The scheduler needs at least one feasible node. A scheduling conflict occurs when every node fails one or more placement requirements. The key is to read the scheduler’s rejection message and map it back to the Pod specification.

Resources

CPU, memory, hugepages, extended resources, Pod count capacity.

Placement

nodeSelector, node affinity, pod affinity/anti-affinity, topology spread.

Node conditions

Taints, unschedulable nodes, pressure conditions, node readiness.

Ports

hostPort can restrict placement when the requested node/port combination is already occupied.

Storage

PVC binding, PV node affinity, allowed topology, attach limits.

Scheduling gates

A Pod may intentionally remain gated until external prerequisites are satisfied.

Compare Pod requirements with node reality
POD=<pod>
NS=<namespace>

kubectl describe pod "$POD" -n "$NS"
kubectl get pod "$POD" -n "$NS" -o yaml
kubectl get nodes -o wide
kubectl get nodes --show-labels
kubectl describe node <node>
kubectl get pod "$POD" -n "$NS" \
  -o jsonpath='{.spec.schedulingGates}{"\n"}'
Do not “fix” scheduling by blindly removing all requests, affinity, taints, or topology rules. Those constraints may encode availability, security, licensing, hardware, or failure-domain requirements. Diagnose the exact conflict first.
Scenario-based incident practice

Diagnose the chain, not a pre-labeled fault

Incident 1 — “The API is timing out”

Initial report: users receive timeouts calling an internal API. Pods are Running.

  1. Confirm Service resolves and exists.
  2. EndpointSlices show no ready addresses.
  3. Service selector and Pod labels match.
  4. Pod readiness is failing on port 8080.
  5. Application is listening on 8081.
Diagnosis

The wrong readiness port keeps Pods out of ready Service backends. Correct the probe after confirming 8081 is intentional, then verify Ready state, EndpointSlice population, and traffic.

Incident 2 — “Deployment stuck after storage change”

  1. Pod Event reports volume node affinity conflict.
  2. PV is restricted to one topology.
  3. Pod required node affinity only permits another topology.
  4. Deleting the Pod cannot satisfy both constraints.
Diagnosis

This is a scheduling/storage topology conflict. Align workload placement and storage topology without compromising data safety.

Incident 3 — “Pod keeps restarting after release”

  1. Read previous logs.
  2. Check Last State and exit code.
  3. Logs report a missing configuration key.
  4. Compare ConfigMap/Secret references with the previous release.
Diagnosis

CrashLoopBackOff is secondary; invalid runtime configuration is the root cause. Correct or roll back configuration and verify stable readiness.

7.5 · Node health & pressure

When the Pod problem is actually a node problem

A node can be reachable from the API yet still be unsuitable for workloads. Distinguish Ready/NotReady from pressure conditions such as MemoryPressure, DiskPressure, and PIDPressure.

NotReady

Investigate kubelet heartbeat/lease, runtime, node networking, and host health.

MemoryPressure

Kubelet has crossed a memory eviction threshold; workloads may be evicted.

DiskPressure

Node filesystem/image filesystem space or inode pressure is present.

PIDPressure

Available process IDs have crossed the configured pressure threshold.

Node triage
kubectl get nodes -o wide
kubectl describe node <node>
kubectl get node <node> \
  -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{"\n"}{end}'
kubectl get pods -A --field-selector spec.nodeName=<node> -o wide
Node-level debug session
kubectl debug node/<node> -it \
  --image=ubuntu:24.04 --profile=sysadmin

# The node filesystem is mounted under /host.
# Inspect host logs directly (paths vary by distribution).
ls -lah /host/var/log
tail -n 200 /host/var/log/syslog 2>/dev/null || true
tail -n 200 /host/var/log/messages 2>/dev/null || true
tail -n 200 /host/var/log/kubelet.log 2>/dev/null || true

# If the host stores a persistent systemd journal:
chroot /host journalctl -u kubelet --since "30 min ago" --no-pager
Node-debug limitation: kubectl debug node/<node> schedules a debugging Pod onto that node. It cannot troubleshoot a node that is fully down, disconnected, or whose kubelet cannot run the debugging Pod; use out-of-band/host access in that case.
Important: pressure-driven evictions are kubelet decisions. Do not diagnose them solely from current usage; inspect node Conditions, Events, requests, priority, and the workload's recent history.
7.6 · Probe failure diagnosis

Readiness, liveness, and startup failures are different incidents

ProbeWhat failure changesTypical symptom
ReadinessPod is removed from Service-ready backendsPod Running but traffic not routed to it
LivenessKubelet restarts the container after threshold is exceededRestarts / CrashLoop-like operational symptom
StartupProtects slow-starting container from liveness/readiness until startup succeedsStartup never completes or thresholds are too strict
kubectl describe pod <pod> -n <ns>
kubectl get pod <pod> -n <ns> -o yaml
kubectl logs <pod> -n <ns> --all-containers=true
kubectl get endpointslices -n <ns> \
  -l kubernetes.io/service-name=<svc> -o wide
Readiness diagnosis: endpoint disappears, but container may stay Running. Validate probe path/port/headers, dependency health, and application readiness semantics.
Liveness anti-pattern: pointing liveness at a fragile downstream dependency can turn a dependency outage into mass container restarts.
7.7 · RBAC & ServiceAccount failures

“Forbidden” is usually an authorization clue, not a networking clue

When an in-cluster client receives HTTP 403 / forbidden, establish the identity first, then ask Kubernetes whether that identity is authorized for the exact verb, resource, namespace, and API group.

# Which ServiceAccount does the Pod use?
kubectl get pod <pod> -n <ns> \
  -o jsonpath='{.spec.serviceAccountName}{"\n"}'

# Test authorization explicitly
kubectl auth can-i get secrets \
  --as=system:serviceaccount:<ns>:<serviceaccount> \
  -n <ns>

kubectl auth can-i --list \
  --as=system:serviceaccount:<ns>:<serviceaccount> \
  -n <ns>

kubectl get role,rolebinding,clusterrole,clusterrolebinding -A
Best practice: fix the smallest missing permission. Avoid “temporary” cluster-admin grants that become permanent operational debt.
Deep dive · identity chain

Pod → ServiceAccount → projected token → API request identity → Role/ClusterRole rules → RoleBinding/ClusterRoleBinding scope. A correct token does not imply authorization.

7.8 · Stuck Terminating resources

Find what is blocking deletion before forcing it

A resource that remains Terminating normally has a deletion timestamp but cleanup has not completed. Common causes include finalizers, unavailable controllers, volume detach/unmount, or a node/kubelet that cannot complete Pod termination.

kubectl get pod <pod> -n <ns> -o yaml
kubectl describe pod <pod> -n <ns>

# Inspect deletion/finalizer fields
kubectl get pod <pod> -n <ns> \
  -o jsonpath='{.metadata.deletionTimestamp}{" finalizers="}{.metadata.finalizers}{"\n"}'

# Check the node and volume-related events before forcing deletion
kubectl get events -n <ns> --sort-by=.lastTimestamp
kubectl get volumeattachments.storage.k8s.io
Force deletion is an escalation step, not normal cleanup. It can remove the API object before the underlying process or storage state is actually gone. Understand the finalizer/node/storage consequence first.

7.10 · CSI driver troubleshooting

Locate whether failure is controller-side or node-side

Provision

Controller/provisioner creates or selects the volume.

Attach

Controller-side attach if the storage system requires it.

Stage/Publish

Node plugin prepares and mounts the volume.

Application

Container sees mountPath, permissions, ownership, and filesystem semantics.

kubectl get csidrivers
kubectl get csinodes
kubectl get volumeattachments.storage.k8s.io
kubectl get pods -A | grep -i csi

kubectl describe pvc <pvc> -n <ns>
kubectl describe pv <pv>
kubectl describe pod <pod> -n <ns>

# Then inspect the driver-specific controller/node Pods:
kubectl logs -n <csi-namespace> <csi-pod> --all-containers --tail=200
Interpretation rule: provisioning errors generally point toward the controller/provisioner path; FailedMount after a node is selected generally moves attention toward kubelet, CSI node plugin, filesystem, credentials, or node-local prerequisites.

Incident 4 — “Pods are disappearing from one worker”

Evidence chain: node reports DiskPressure=True; kubelet Events show evictions; image/log/data usage has consumed node filesystem capacity.

Diagnosis and corrective action

Treat this as a node-pressure incident, not an application crash. Identify disk/inode consumers, validate image/log rotation and ephemeral-storage requests/limits, recover capacity safely, then confirm the node condition clears and scheduling behavior normalizes.

Incident 5 — “Application can reach the API server but gets forbidden”

Evidence chain: network connection succeeds; API returns 403; Pod ServiceAccount lacks the requested verb on the resource.

Diagnosis and corrective action

Use kubectl auth can-i with the Pod ServiceAccount identity, correct the least-privilege Role/Binding, and retest. Do not treat an authorization denial as a CNI failure.

7.5 · Hands-on labs

Controlled failures you can diagnose safely

Lab scope: use a dedicated training cluster. Commands create and delete namespace-scoped resources. Do not run disruption-oriented variants on shared production clusters. The cluster nodes must also be able to pull the example container images from their referenced registries, or you should substitute equivalent images from your approved internal registry.

7. Rule

  • Collect before deleting.
  • Change one proven cause at a time.
  • Verify the user path after the fix.
7.6 · Best practices

Make troubleshooting repeatable

Never make these your first troubleshooting action:
  • delete Pods before collecting Events/logs;
  • remove requests, affinity, taints, NetworkPolicies, or security controls merely to “make it work”;
  • edit bound PVs/storage topology without understanding data consequences;
  • restart kubelet/runtime/control-plane components before proving the fault is there;
  • treat Running as proof that the application is healthy or reachable.

Operational habits

Escalation ladder

  1. Object state and Events.
  2. Application logs and previous container logs.
  3. Service/endpoints/DNS/policy checks.
  4. Node conditions, kubelet/runtime, CNI/CSI components.
  5. Control-plane/component logs and implementation-specific diagnostics.

Knowledge check

1. A Pod is Pending and has no assigned node. What is the best first evidence source?
2. A Service resolves in DNS but its EndpointSlice contains no ready backend addresses. Which area should you inspect first?
3. Which statement about scheduling and resource usage is most accurate?
Core principle: every troubleshooting step should answer one question. If the command you run cannot prove or disprove a hypothesis, it is probably noise rather than diagnosis.
