Module 8 • Closure & Outcomes

From Kubernetes Features to Production Decisions

This closure module is designed to answer a more important question than “did you finish the labs?”: can you combine scheduling, identity, traffic, storage, health and troubleshooting concepts into safe operational decisions?

Learning goal: by the end, you should be able to explain not only what a Kubernetes control does, but why you would use it, what it changes in the cluster, how to verify it, and how to troubleshoot it when reality differs from design.

2. What “successful completion” actually means

The following outcomes are framed as production capabilities. Each outcome connects design intent, implementation mechanisms and operational evidence.

Outcome 01

Advanced scheduling

Design placement rules that express hardware needs, failure-domain intent, co-location/anti-co-location, dedicated capacity and disruption tolerance without making the scheduler impossible to satisfy.

Outcome 02

Workload security

Reduce identity and network blast radius with purpose-specific ServiceAccounts, minimal RBAC, token hygiene, NetworkPolicies and secure pod defaults.

Outcome 03

Safe service exposure

Expose workloads through Services and Ingress with correct host/path routing, TLS termination, backend health awareness and a clear understanding of what the ingress controller actually implements.

Outcome 04

Persistent storage

Choose and verify StorageClass, PV/PVC, access mode, binding mode, reclaim behavior and failure-domain decisions so application data survives pod replacement safely.

Outcome 05

Troubleshooting

Work from symptom → Kubernetes object state → event → dependency → node/network/storage evidence instead of guessing or immediately restarting components.

Meta-skill

Operational verification

Treat YAML as desired state, not proof. Verify scheduler decisions, endpoints, identities, policies, mounts, events and traffic paths after every significant change.

Assumed from earlier modules: Deployments, Pods, Services, namespaces, labels/selectors, kubectl basics, container logs and basic cluster networking are already familiar. If any of those are weak, use this document as a map of what to revisit rather than memorizing the commands.

3. One integrated production model

A production workload is never “just a Pod.” Its behavior emerges from multiple control planes and data paths working together.

Operational insight: when an application fails, the visible symptom may be several layers away from the cause. An HTTP 503 could be an ingress problem, but it could also be zero ready endpoints, a failed readiness probe, a selector mismatch, a denied network path, a Pending pod, or a storage-related startup failure.

4. Outcome: design advanced scheduling strategies

Production scheduling is constraint design. The goal is not to use every feature; it is to express the minimum set of constraints needed for reliability, compliance and performance.

Hard constraints

Use when placement is invalid unless a condition is true.

  • nodeSelector
  • requiredDuringSchedulingIgnoredDuringExecution
  • Untolerated taints
  • Volume topology constraints

Soft preferences

Use when a placement is better, but alternatives are acceptable.

  • preferredDuringSchedulingIgnoredDuringExecution
  • Topology spread preferences
  • Weighted affinity terms
RequirementMechanismProduction caution
Dedicated GPU/workload nodesTaints + tolerations, usually paired with node affinityA toleration permits placement; it does not force the pod onto that node.
Spread replicas across zones/nodesTopology spread constraints or pod anti-affinityOverly strict anti-affinity can create Pending pods during failure or scale-out.
Keep tightly-coupled workloads near each otherPod affinityCoupling can reduce resilience if all replicas share one failure domain.
Storage topology alignmentWaitForFirstConsumer + CSI topology awarenessImmediate volume creation can select storage before pod placement is known.
kubectl get pods -A -o wide
kubectl describe pod <pod> -n <namespace>
kubectl get nodes --show-labels
kubectl describe node <node>
kubectl get events -A --sort-by=.lastTimestamp | tail -n 40

Evidence you want: the pod landed on an intended node, the event stream explains why, and the rules still allow acceptable placement when a node or zone becomes unavailable.

5. Outcome: secure workloads with ServiceAccounts and NetworkPolicies

Identity and connectivity should both be explicit. The secure target is not “no access”; it is only the access the workload needs.

ServiceAccount = workload identity

  • Create purpose-specific ServiceAccounts.
  • Bind only the RBAC permissions required.
  • Avoid using the namespace default ServiceAccount for privileged application actions.
  • Disable automatic token mounting when the workload does not need Kubernetes API credentials.

NetworkPolicy = allowed network relationships

  • Start from intended flows: who must call whom?
  • Understand that enforcement depends on a NetworkPolicy-capable CNI.
  • Default-deny patterns are useful only when required DNS, control, metrics and application flows are deliberately re-allowed.
  • Policies are additive: the allowed traffic is the union of applicable rules.
Secure workload example
apiVersion: v1
kind: ServiceAccount
metadata:
  name: api
  namespace: prod
automountServiceAccountToken: false
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-ingress
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
Verify, do not assume: a valid NetworkPolicy object proves only that the API accepted it. Test the path from an allowed source and a denied source. Also verify your CNI actually enforces NetworkPolicy.

6. Outcome: expose services safely using Ingress

The earlier ingress traffic-management module focused on host/path routing, TLS and controller behavior. The closure skill is to trace the complete request path and identify the layer that owns each failure.

1. Client resolves and connects

DNS, IP reachability, load balancer/listener and TLS handshake must succeed before Kubernetes routing is relevant.

2. Ingress rule matches

Host, path and pathType determine the intended backend. The ingress controller implements the rule.

3. Service selects endpoints

The Service selector must match pods. Ready endpoint membership matters.

4. Policy allows the flow

If NetworkPolicy isolates a pod, required ingress/egress paths must be allowed.

5. Application responds

Container port, application bind address, protocol, readiness and backend latency complete the path.

kubectl get ingress -A
kubectl describe ingress <name> -n <namespace>
kubectl get svc,endpoints,endpointslices -n <namespace>
kubectl get pods -n <namespace> -o wide
kubectl logs -n <ingress-controller-namespace> deploy/<controller-deployment>

7. Outcome: manage persistent storage reliably

Reliable persistence means understanding the whole binding and attachment chain, not merely seeing a PVC in Bound state.

LayerQuestion to answerTypical evidence
StorageClassWhich provisioner and policy create the volume?kubectl get sc -o yaml
PVCWhat capacity, access mode and class did the workload request?kubectl describe pvc
PVWhat was actually provisioned and with what reclaim behavior?kubectl get pv, describe pv
CSIDid provisioning, attachment and mount operations succeed?Events + CSI controller/node plugin logs
PodDid the volume mount at the expected path and is the application able to use it?describe pod, mount checks, application logs
Failure-domain connection: storage and scheduling are coupled. A dynamically provisioned topology-aware volume may constrain where a pod can run. This is why WaitForFirstConsumer is important for many zonal/local storage systems.

8. Outcome: troubleshoot complex Kubernetes issues confidently

The most reusable troubleshooting method is evidence-driven narrowing. Start with object state and events before changing anything.

First question

Why did the scheduler not bind this pod?

kubectl describe pod <pod> -n <ns>
kubectl get events -n <ns> --sort-by=.lastTimestamp

Common evidence

  • Insufficient CPU/memory
  • Untolerated taint
  • Node selector/affinity mismatch
  • Unbound PVC
  • Topology or anti-affinity conflict

Trace layer by layer

DNS → Service selector → EndpointSlice → policy → pod listener → application.

Useful checks

kubectl get svc,endpointslices -n <ns>
kubectl exec -n <ns> <pod> -- getent hosts <service>
kubectl exec -n <ns> <pod> -- wget -S -O- http://<service>:<port>
kubectl get networkpolicy -A

Mount failure sequence

Pod event → PVC state → PV state → StorageClass → CSI controller/node logs → node filesystem/device evidence.

Do not skip

Read the event text exactly. “Provisioning failed,” “attach failed,” and “mount failed” are different stages with different owners.

Constraint collision

A pod can satisfy each rule independently but fail when rules are combined: affinity + taints + resources + volume topology + anti-affinity.

Technique

List every hard scheduling constraint, then compare the intersection against real nodes. Remove or relax one condition only when the design permits it.

Universal troubleshooting loop
  1. State the symptom precisely. “Pod Pending for 6 minutes” is better than “deployment broken.”
  2. Identify the responsible object. Pod? Service? Ingress? PVC? Node?
  3. Inspect current state. get and describe.
  4. Read events. Kubernetes often tells you which control-plane decision failed.
  5. Trace dependencies outward. Selector, ServiceAccount, policy, PVC, CSI, node, DNS, CNI.
  6. Change one thing. Avoid simultaneous fixes that destroy evidence.
  7. Verify recovery and intended behavior. “Running” is not the same as “correct.”

9. Integrated production incident simulation

This exercise deliberately mixes multiple layers. Work from evidence; do not jump to the apparent symptom.

Incident: users report intermittent 503 Service Unavailable from https://shop.example.com/api. A rollout completed 10 minutes ago.
Step 1 — ObserveIngress reports backend unavailable.
Step 2 — Check endpointsThe Service has zero ready endpoints.
Step 3 — Inspect podsOne pod is Running but NotReady; another is Pending.
Step 4 — Split the problemReadiness failure on one replica; scheduling/storage conflict on the other.
Step 5 — Recover and verifyFix probe target and restore satisfiable storage-aware placement.
# Step 1 curl -I https://shop.example.com/api HTTP/2 503 kubectl describe ingress shop -n prod # Rule matches /api and points to service api:8080 Conclusion: The client reaches the ingress controller. Do not debug DNS first.

11. Safe failure-injection mini-labs

These labs intentionally break a small part of a workload so trainees practice diagnosis and recovery. Use a disposable namespace, never a production namespace.

Lab safety: set a dedicated namespace first, e.g. export NS=closure-lab. Delete it after the exercises with kubectl delete ns "$NS".
Failure injectionRequires working cluster

Lab A — Break a readiness probe

Goal: prove that a Running pod can be removed from Service endpoints when readiness fails.

export NS=closure-lab
kubectl create ns "$NS" --dry-run=client -o yaml | kubectl apply -f -

kubectl -n "$NS" create deployment web --image=nginx:1.27
kubectl -n "$NS" expose deployment web --port=80

kubectl -n "$NS" patch deployment web --type='json' -p='[
  {"op":"add","path":"/spec/template/spec/containers/0/readinessProbe",
   "value":{"httpGet":{"path":"/does-not-exist","port":80},
            "initialDelaySeconds":2,"periodSeconds":3}}
]'

kubectl -n "$NS" get pods -w
kubectl -n "$NS" get endpointslices -l kubernetes.io/service-name=web

Expected reasoning: container remains Running, readiness fails, and the pod is not considered a ready backend for normal Service traffic. Recover by changing the probe path to / or removing the intentionally broken probe.

Failure injectionScheduling

Lab B — Create an unschedulable pod

Goal: diagnose a Pending pod caused by an impossible node selector.

cat <<'EOF' | kubectl apply -n "$NS" -f -
apiVersion: v1
kind: Pod
metadata:
  name: impossible-placement
spec:
  nodeSelector:
    closure.lab/nonexistent: "true"
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.10
EOF

kubectl -n "$NS" describe pod impossible-placement
kubectl get nodes --show-labels

Expected reasoning: the scheduler cannot find a node satisfying the hard selector. The correct fix is to change the intended placement rule or label an appropriate node only if that reflects the real design.

Failure injectionService routing

Lab C — Break the Service selector

Goal: separate a healthy workload from a broken Service-to-Pod relationship.

kubectl -n "$NS" patch service web --type='merge' -p \
'{"spec":{"selector":{"app":"wrong-label"}}}'

kubectl -n "$NS" get svc web -o yaml
kubectl -n "$NS" get endpointslices -l kubernetes.io/service-name=web
kubectl -n "$NS" get pods --show-labels

# Recover:
kubectl -n "$NS" patch service web --type='merge' -p \
'{"spec":{"selector":{"app":"web"}}}'

Expected reasoning: the application pods can be healthy while the Service has no matching endpoints. Always compare Service selectors with real pod labels.

15. Final capstone — defend a production workload design

Use this as the final practical closure exercise. The objective is not to produce the largest YAML file; it is to make defensible operational choices.

Scenario

You operate a three-tier application: public frontend, internal API and PostgreSQL-like stateful datastore. The cluster spans multiple worker nodes and uses a NetworkPolicy-capable CNI plus a CSI driver.

  1. Place API replicas across failure domains without making rescheduling impossible.
  2. Give each tier an appropriate ServiceAccount and justify API token mounting.
  3. Allow frontend → API and API → database traffic while blocking unrelated paths.
  4. Expose only the frontend through Ingress with TLS.
  5. Define readiness/liveness/startup behavior suitable for each tier.
  6. Choose storage binding and reclaim behavior for the stateful tier.
  7. Write a five-step first-response runbook for an HTTP 503.
  8. Define the evidence that proves the deployment is production-ready.

What a strong answer demonstrates

  • Hard vs soft scheduling constraints are distinguished.
  • Security is based on least privilege, not convenience.
  • Network intent is documented before policy YAML.
  • Ingress, Service and readiness dependencies are understood.
  • Storage and scheduling topology are considered together.
  • Troubleshooting starts with evidence and narrows systematically.
Reference solution outline — reveal after attempting
  • Scheduling: topology spread or preferred anti-affinity across hostname/zone; avoid unnecessary hard anti-affinity.
  • Identity: dedicated ServiceAccounts; disable automount where Kubernetes API access is unnecessary; bind minimal RBAC only where needed.
  • Network: default-deny-compatible policy design, then explicit frontend→API and API→database allowances plus required DNS/operational traffic.
  • Ingress: frontend only; TLS configured; backend Service verified to have ready endpoints.
  • Health: readiness represents traffic eligibility; liveness detects unrecoverable process failure; startup probes protect slow initialization.
  • Storage: CSI-backed class appropriate to workload topology, commonly WaitForFirstConsumer for topology-sensitive dynamic provisioning; deliberate reclaim policy.
  • 503 runbook: ingress rule/controller → Service selector → EndpointSlice → pod readiness → NetworkPolicy/application.
  • Verification: placement, identities, endpoint membership, allowed/denied traffic tests, TLS path, PVC/PV state, failure drill and recovery evidence.

12. What comes next

This module closes the feature-oriented learning sequence. The next progression should move from individual controls to cluster operations and reliability engineering.

Observability

Metrics, logs, traces, events, SLOs, Prometheus/Grafana, alert design and workload-level golden signals.

Resilience engineering

PodDisruptionBudgets, graceful termination, rollout strategy, autoscaling, capacity planning, node maintenance and failure drills.

Platform operations

Admission control, policy engines, supply-chain security, GitOps, backup/restore, upgrade planning and multi-tenant guardrails.

Closure challenge: take one real application and document its scheduling rules, ServiceAccount/RBAC, NetworkPolicies, Ingress path, probes, storage dependencies and a five-step troubleshooting runbook. If you can defend those choices and verify them in-cluster, the training outcomes have become operational skill.
