Custom Resource Definitions in Kubernetes

A deep, practical guide to extending the Kubernetes API with your own resource types—without writing a new API server. The emphasis is not merely on “creating a CRD”, but on understanding API design, schema, validation, lifecycle, versioning, RBAC, reconciliation, debugging, and safe production evolution.

Series continuity. In the earlier Ingress traffic-management material, Kubernetes objects described desired network exposure while controllers translated them into runtime behavior. CRDs generalize that same pattern: define a new declarative API, then optionally pair it with a controller that continuously reconciles desired state into real state.

2. The mental model: extend the API, then optionally automate it

A Custom Resource (CR) is an instance of a type that is not part of Kubernetes’ built-in API. A CustomResourceDefinition (CRD) registers that type with the API server. Once registered, the API behaves as though a new resource family exists: it participates in API discovery, validation, storage, RBAC, watch/list/get operations and normal kubectl workflows.

Critical distinction: a CRD gives Kubernetes a new data model and REST endpoint. It does not, by itself, create Deployments, configure databases, rotate certificates, back up applications, or perform any other business action. Automation comes from a controller/operator that watches the custom resources and reconciles them.

3. Anatomy of a CRD — from YAML to a new Kubernetes API

A CRD can look intimidating because it contains several layers of YAML, but the idea is much simpler than the file first suggests. A CRD answers four basic questions:

1. What is the new resource called?
WebApp, webapps, short name wa.
2. Where does it live in the Kubernetes API?
API group platform.gnugroup.org, version v1alpha1.
3. Is it namespaced or cluster-wide?
scope: Namespaced or scope: Cluster.
4. What data is allowed inside it?
The OpenAPI schema defines fields such as image and replicas.
The simplest mental model: a CRD is like registering a new Kubernetes object type. Once the CRD is accepted, the API server knows that objects of that type exist, what they are called, where their REST endpoint lives, which versions are available, and what their data should look like.

3.1 CRD versus Custom Resource

This is the most important distinction in the entire topic.

3.2 See the hierarchy before reading individual lines

The CRD YAML can be divided into five logical areas:

3.3 Start at the top: apiVersion and kind

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition

These two lines describe the CRD object itself, not the WebApp objects that will be created later.

LinePlain-language meaning
apiVersion: apiextensions.k8s.io/v1 Use Kubernetes' built-in API-extension API to define a custom resource type.
kind: CustomResourceDefinition The object being submitted is a CRD registration.
Do not confuse this with the custom resource's API version. The CRD itself uses apiextensions.k8s.io/v1. A WebApp object created later uses platform.gnugroup.org/v1alpha1.

3.4 metadata.name: the CRD's registration name

metadata:
  name: webapps.platform.gnugroup.org

Kubernetes requires the CRD name to be built from:

<plural>.<group>

webapps + . + platform.gnugroup.org
↓
webapps.platform.gnugroup.org

This is the name you use when managing the CRD itself:

kubectl get crd webapps.platform.gnugroup.org
kubectl describe crd webapps.platform.gnugroup.org
Common error: if metadata.name does not match spec.names.plural + "." + spec.group, Kubernetes rejects the CRD.

3.5 spec.group: choose the API group

spec:
  group: platform.gnugroup.org

The API group is the namespace of your API—not a Kubernetes namespace, but a logical API family. It prevents your resource name from colliding with another vendor's or project's resource.

For example:

GroupPossible owner/purpose
appsBuilt-in Kubernetes application APIs such as Deployment.
networking.k8s.ioBuilt-in Kubernetes networking APIs.
cert-manager.ioAn extension API owned by the cert-manager project.
platform.gnugroup.orgExample custom platform API used in this training module.

Once combined with a version, this becomes the apiVersion used by Custom Resources:

apiVersion: platform.gnugroup.org/v1alpha1
Good practice: use a DNS-style group associated with a domain your organization controls. It gives the API a clear ownership boundary and reduces naming conflicts.

3.6 scope: does each object belong to a namespace?

scope: Namespaced

The scope determines where CR instances live.

ScopeMeaningExamples of suitable concepts
Namespaced Each object belongs to one Kubernetes namespace. Application, database request, backup policy, tenant workload.
Cluster The object exists once at cluster scope and has no namespace. Cluster-wide infrastructure policy, global node-management configuration.

For a namespaced WebApp:

metadata:
  name: payments
  namespace: production

The REST path contains the namespace:

/apis/platform.gnugroup.org/v1alpha1/namespaces/production/webapps/payments

For a cluster-scoped custom resource, the /namespaces/production portion is absent.

Useful distinction: the CRD definition itself is cluster-scoped even when the custom resources created from it are namespaced.

3.7 names: teach Kubernetes the resource vocabulary

names:
  plural: webapps
  singular: webapp
  kind: WebApp
  shortNames:
    - wa

These fields control how humans, manifests, clients and REST paths refer to the resource.

FieldUsed forExample
plural REST collection and normal kubectl get resource name. kubectl get webapps
singular Singular CLI/display alias. kubectl get webapp payments
kind The value written in YAML manifests. kind: WebApp
shortNames Convenient CLI aliases. kubectl get wa
Naming rules matter. plural, singular, and short names are lowercase resource names. kind is normally a singular CamelCase name such as WebApp.

3.8 versions: expose one or more versions of your API

versions:
  - name: v1alpha1
    served: true
    storage: true

A CRD can support multiple API versions during its lifetime—for example:

v1alpha1  →  v1beta1  →  v1

Each version has two especially important switches:

FieldQuestion it answers
served: true “May clients send API requests using this version?”
storage: true “Is this the canonical version Kubernetes uses when persisting this custom resource?”
Rule: a CRD can serve multiple versions, but exactly one version must be marked storage: true.

A multi-version picture

versions:
  - name: v1alpha1
    served: true
    storage: false

  - name: v1
    served: true
    storage: true

Clients can use either served version, while Kubernetes persists the resource using the configured storage version. If the versions differ semantically, a conversion strategy is needed; that is covered later in the module.

3.9 schema: describe what a valid WebApp looks like

This is where you define the data contract for each version.

schema:
  openAPIV3Schema:
    type: object
    properties:
      spec:
        type: object
        properties:
          image:
            type: string
          replicas:
            type: integer

Read the YAML from the outside inward:

Whole CR
type: object
The entire WebApp document is an object.
spec
type: object
The desired configuration is another nested object.
spec.image
type: string
The value must be text.
spec.replicas
type: integer
The value must be an integer.

With this schema, a valid object might look like:

spec:
  image: nginx:1.27
  replicas: 3

Whereas this would be invalid if the schema requires an integer:

spec:
  replicas: "three"   # string, not integer
The schema does three jobs: it helps Kubernetes validate data, prune unknown fields according to structural-schema rules, and support features such as defaulting. Section 4 goes deeper into all three.

3.13 What Kubernetes has after the CRD is created

After Kubernetes accepts the CRD, it now has:

API discovery entry
Clients can discover webapps.platform.gnugroup.org.
REST endpoints
Clients can create, read, update, list, watch and delete WebApp objects, subject to RBAC.
Schema knowledge
The API server can validate/prune/default fields according to the CRD.
Persistent objects
Accepted Custom Resources can be persisted through the Kubernetes API storage path.
Watchable events
A future controller can watch WebApp objects and react to changes.
Still no application behavior
The CRD alone does not create Pods, Deployments or Services.
Repeat this until it becomes automatic:
CRD = define the API.
CR = store desired data in that API.
Controller = turn that desired data into real behavior.

3.14 Common trainee confusions

“Why are there two kinds in the examples?”

The CRD document has kind: CustomResourceDefinition because that object registers a new type. The resource created later has kind: WebApp because it is an instance of the newly registered type.

“Why does the CRD use one apiVersion but WebApp uses another?”

The CRD object belongs to Kubernetes' built-in API extension system: apiextensions.k8s.io/v1. The WebApp belongs to the API you created: platform.gnugroup.org/v1alpha1.

“Does v1alpha1 mean Kubernetes itself is alpha?”

No. It describes the maturity/version of your WebApp API, not Kubernetes itself.

“Does scope: Namespaced make the CRD namespaced?”

No. The CRD registration remains cluster-scoped. The setting means that WebApp instances are namespaced.

“Does defining replicas make Kubernetes create replicas?”

No. The schema only allows and validates the field. A controller must read spec.replicas and create or update actual workload resources.

“Why not put everything under metadata?”

metadata has Kubernetes-defined semantics for identity and object management. Your domain configuration normally belongs under fields such as spec, while observed controller state commonly belongs under status.

ASSUMED FROM HERE Later sections use the normal Kubernetes convention that spec represents desired state and status represents observed state. You do not need a controller yet to understand the CRD, but status becomes much more meaningful once a controller is introduced.

3.15 Five-question checkpoint

1. What does the CRD create: an application or an API resource type?
An API resource type. Application behavior requires a controller or another actor.
2. From where does apiVersion: platform.gnugroup.org/v1alpha1 come?
It combines spec.group with versions[].name.
3. What determines the word used in kubectl get webapps?
spec.names.plural.
4. What determines whether a CR needs a namespace?
spec.scope.
5. What decides whether replicas: "three" is legal?
The version's schema.openAPIV3Schema. If replicas is defined as an integer, the string value is rejected.

4. Schema, validation, defaulting and pruning

A production CRD is an API contract. The schema should prevent invalid states early and make the object understandable to clients and humans.

schema:
  openAPIV3Schema:
    type: object
    required: ["spec"]
    properties:
      spec:
        type: object
        required: ["image"]
        properties:
          image:
            type: string
            minLength: 1
          replicas:
            type: integer
            minimum: 1
            maximum: 10
          exposure:
            type: string
            enum: ["ClusterIP", "Ingress"]

Reject impossible or unsupported requests at admission time rather than relying on a controller to discover them later.

replicas:
  type: integer
  minimum: 1
  maximum: 10
  default: 1

Defaults are applied according to the CRD schema. A default is part of your API behavior; changing it later can alter how newly created objects behave.

Unknown fields not represented by the structural schema are generally pruned. If you intentionally need free-form nested data, Kubernetes provides extension mechanisms such as x-kubernetes-preserve-unknown-fields, but broad use weakens validation and API clarity.

CRDs can express richer validation using Kubernetes Common Expression Language (CEL) through x-kubernetes-validations. CRD validation rules using CEL are stable (GA) in modern Kubernetes releases; they are useful for invariants that involve multiple fields.

x-kubernetes-validations:
  - rule: "self.minReplicas <= self.maxReplicas"
    message: "minReplicas must not exceed maxReplicas"

Schema design rule

Prefer “make invalid states unrepresentable.” Use required fields, enums, numeric ranges, formats, object shape and cross-field validation where appropriate. The controller should focus on reconciliation—not basic input hygiene.

5. What happens when a Custom Resource is submitted?

The exact admission chain depends on cluster configuration, but custom resources participate in the Kubernetes API machinery. CRDs do not bypass the platform’s authorization model.

6. CRD vs controller/operator

CRD

Defines the API type and schema. API server stores and serves instances. Think: noun.

WebApp, Database, BackupPolicy.

Controller

Watches objects and drives actual state toward desired state. Think: reconciliation behavior.

Create Deployment, Service, Secret, cloud resource, status conditions, etc.

Operator

A controller focused on automating domain knowledge and lifecycle operations, usually through one or more custom APIs.

Do not fake reconciliation in a CRD schema. Schema describes accepted data. It is not a workflow engine. If desired state must cause external effects, use a controller, operator, admission component, or another service suited to that responsibility.

7. Advanced CRD features that make the API usable

7.1 Status subresource

Enable /status so controllers can update observed state separately from user-authored desired state.

subresources:
  status: {}

Recommended status fields include observedGeneration and standard-style conditions. A controller can compare metadata.generation to status.observedGeneration to signal whether the current spec has been observed.

For production APIs, model conditions deliberately (commonly including type, status, reason, message, lastTransitionTime and, where useful, observedGeneration) and consider Kubernetes list-map semantics when the controller-runtime/API design requires stable condition merging.

7.2 Scale subresource

For workload-like APIs, the scale subresource can integrate with clients that understand the Kubernetes scale contract.

subresources:
  status: {}
  scale:
    specReplicasPath: .spec.replicas
    statusReplicasPath: .status.replicas
    labelSelectorPath: .status.selector

7.3 Additional printer columns

additionalPrinterColumns:
  - name: Image
    type: string
    jsonPath: .spec.image
  - name: Replicas
    type: integer
    jsonPath: .spec.replicas
  - name: Phase
    type: string
    jsonPath: .status.phase
  - name: Age
    type: date
    jsonPath: .metadata.creationTimestamp

7.4 Finalizers

A finalizer is a deletion gate. Controllers add a string to metadata.finalizers when external cleanup must occur before the API object disappears. When deletion is requested, Kubernetes sets deletionTimestamp; the controller cleans up and removes its finalizer.

Operational risk: a broken controller can leave objects stuck in Terminating because its finalizer is never removed. Never strip a finalizer blindly in production; first understand what cleanup it protects.

8. Versioning, storage and conversion

A CRD can serve multiple API versions. This is an API-evolution tool, not merely a label change.

FlagMeaning
served: trueThe API server accepts/returns requests for this version.
storage: trueThis version is used to persist objects. Exactly one version is storage.

With conversion strategy None, Kubernetes changes the apiVersion presented to clients but does not perform semantic transformation of fields; pruning may still occur according to schema. Use this only when the served versions are schema-compatible for your use case.

A conversion webhook is required when versions represent data differently—for example, spec.size becomes spec.resources.requests.storage. The API server calls the webhook when conversion is needed between served and stored versions.

Changing the storage version does not automatically rewrite pre-existing objects in etcd. New or updated objects are written using the current storage version. Production API upgrades therefore need an explicit storage-migration procedure (for example, Storage Version Migration where appropriate) and verification of status.storedVersions.

ADVANCED ASSUMPTION Conversion webhooks assume you understand HTTPS Services, certificates/CA bundles, API server reachability, admission-style request/response handling and highly available webhook deployment. Those are beyond the basic CRD labs below.

Version naming

Typical progression is v1alpha1 → v1beta1 → v1. These labels communicate stability expectations; they should correspond to an intentional compatibility policy.

9. RBAC, tenancy and security boundaries

Custom resources use Kubernetes authentication, authorization and audit mechanisms. Creating a CRD does not automatically grant ordinary users permission to use it.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: crd-lab
  name: webapp-editor
rules:
  - apiGroups: ["platform.gnugroup.org"]
    resources: ["webapps"]
    verbs: ["get","list","watch","create","update","patch","delete"]

If a controller writes status, its RBAC typically needs the webapps/status subresource as well.

- apiGroups: ["platform.gnugroup.org"]
  resources: ["webapps/status"]
  verbs: ["get","patch","update"]
Scope is security architecture. Prefer Namespaced when ownership and tenancy naturally map to namespaces. Choose Cluster only for genuinely cluster-wide concepts.

Lab 1 — Register a production-shaped WebApp CRD

How to read this lab: the YAML below is intentionally heavily commented. The comments are valid YAML and do not change the object, so trainees can copy the complete block exactly as shown. Read the comments before applying it, then use kubectl explain and kubectl get crd ... -o yaml to connect the declaration with what Kubernetes registered.
cat > /tmp/webapp-crd.yaml <<'EOF'
# CRDs are registered through the Kubernetes API extensions group.
apiVersion: apiextensions.k8s.io/v1

# This object tells Kubernetes to create a brand-new API resource type.
kind: CustomResourceDefinition

metadata:
  # CRD names MUST follow: <plural-resource-name>.<api-group>
  # plural = webapps
  # group  = platform.gnugroup.org
  name: webapps.platform.gnugroup.org

spec:
  # The API group under which WebApp resources will be exposed.
  # Custom resources will use:
  # apiVersion: platform.gnugroup.org/v1alpha1
  group: platform.gnugroup.org

  # Namespaced means every WebApp belongs to a Kubernetes namespace.
  # Use "Cluster" only for genuinely cluster-wide resources.
  scope: Namespaced

  # Human-facing and REST-facing names for the new resource.
  names:
    # REST collection name: kubectl get webapps
    plural: webapps

    # Singular resource name: kubectl get webapp <name>
    singular: webapp

    # YAML kind used inside Custom Resource manifests.
    kind: WebApp

    # Optional short alias: kubectl get wa
    shortNames: ["wa"]

    # Include this resource when using kubectl get all.
    categories: ["all"]

  # A CRD may expose one or more API versions.
  versions:
    # v1alpha1 normally indicates an early/evolving API.
    - name: v1alpha1

      # Clients are allowed to use this version.
      served: true

      # Objects are persisted using this version.
      # Exactly ONE version must have storage: true.
      storage: true

      # Improve the default kubectl get webapps table.
      additionalPrinterColumns:
        # Show .spec.image as an IMAGE column.
        - name: Image
          type: string
          jsonPath: .spec.image

        # Show desired replica count.
        - name: Replicas
          type: integer
          jsonPath: .spec.replicas

        # Show controller-reported lifecycle state.
        # This may remain empty in this CRD-only lab.
        - name: Phase
          type: string
          jsonPath: .status.phase

        # Show object creation age.
        - name: Age
          type: date
          jsonPath: .metadata.creationTimestamp

      # Enable the /status API subresource.
      # A controller can then update observed state separately from spec.
      subresources:
        status: {}

      # Define the accepted structure of WebApp objects.
      schema:
        openAPIV3Schema:
          # The complete custom resource is a JSON/YAML object.
          type: object

          # Every WebApp must contain a spec section.
          required: ["spec"]

          properties:
            # spec = desired state supplied by the user.
            spec:
              type: object

              # image must be provided explicitly.
              required: ["image"]

              properties:
                # Container image a future controller could deploy.
                image:
                  type: string

                  # Reject an empty image string.
                  minLength: 1

                # Desired application replica count.
                replicas:
                  type: integer

                  # At least one replica is required.
                  minimum: 1

                  # Limit this training API to ten replicas.
                  maximum: 10

                  # If omitted, Kubernetes defaults it to 1.
                  default: 1

                # Desired exposure mechanism.
                exposure:
                  type: string

                  # Only these values are accepted.
                  enum: ["ClusterIP", "Ingress"]

                  # Default if exposure is omitted.
                  default: "ClusterIP"

                # Application listening port.
                port:
                  type: integer

                  # Restrict the value to the valid TCP/UDP port range.
                  minimum: 1
                  maximum: 65535

                  # Default application port.
                  default: 8080

            # status = observed state, normally owned by a controller.
            status:
              type: object

              properties:
                # Reports which metadata.generation a controller processed.
                observedGeneration:
                  type: integer
                  format: int64

                # Simple example lifecycle state such as Pending or Ready.
                phase:
                  type: string

                # Structured controller conditions such as Ready=True.
                conditions:
                  type: array

                  # Each list entry is a condition object.
                  items:
                    type: object

                    # Every condition identifies its type and state.
                    required: ["type", "status"]

                    properties:
                      # Example values: Ready, Available, Progressing.
                      type:
                        type: string

                      # Kubernetes-style three-state condition value.
                      status:
                        type: string
                        enum: ["True", "False", "Unknown"]

                      # Short machine-readable explanation.
                      reason:
                        type: string

                      # Human-readable explanation.
                      message:
                        type: string

                      # Time when this condition last changed state.
                      lastTransitionTime:
                        type: string
                        format: date-time
EOF
kubectl apply -f /tmp/webapp-crd.yaml
kubectl wait --for=condition=Established "crd/$CRD" --timeout=60s

Verify:

kubectl get crd "$CRD"
kubectl describe crd "$CRD"

Expected: the API server rejects the object because multiple schema constraints are violated. Read the error from top to bottom; it identifies the failing paths.

Lab 5 — Observe generation and status separation

First inspect metadata.generation:

kubectl get webapp demo -n "$LAB_NS" \
  -o jsonpath='generation={.metadata.generation}{"\n"}status={.status}{"\n"}'

kubectl patch webapp demo -n "$LAB_NS" --type=merge \
  -p '{"spec":{"replicas":4}}'

kubectl get webapp demo -n "$LAB_NS" \
  -o jsonpath='generation={.metadata.generation}{"\n"}spec.replicas={.spec.replicas}{"\n"}'

Changing spec increments generation. In a real controller, reconciliation would eventually report that generation through status.observedGeneration.

Status note: this lab intentionally does not pretend that a human is a controller. If you experiment with updating /status, use subresource-aware tooling and understand the RBAC implications. The conceptual requirement is that users own desired state while controllers report observed state.

Lab 8 — Safe cleanup

kubectl delete namespace "$LAB_NS"
kubectl delete crd "$CRD"
Important: deleting a CRD uninstalls its REST endpoint and causes the custom resources stored under that CRD to be deleted. Recreating the same CRD later does not restore those objects. Treat CRD deletion as a destructive API/data lifecycle operation outside disposable labs.

12. Production API design checklist

API ownership
Use a stable domain/group and documented owner. Treat the CRD like a product API.
Scope
Namespaced by default when tenant ownership is meaningful; Cluster only when conceptually global.
Schema first
Validate required fields, ranges, enums and cross-field invariants.
Status contract
Use observedGeneration and conditions; do not echo the entire spec into status.
Idempotent controller
Reconciliation must safely repeat. Events may be duplicated and order is not a transaction log.
Ownership
Use owner references where garbage collection semantics are appropriate; use finalizers for external cleanup.
Version discipline
Plan backward compatibility, deprecation, conversion and storage migration before changing schemas.
API server storage
Do not use CRDs as a generic application database, monitoring store or high-volume event stream.
Security
Least-privilege controller RBAC; separate human and controller permissions; audit mutations.
Observability
Controller metrics, reconciliation errors, work-queue behavior, conditions, Kubernetes Events and structured logs.

When a CRD is a good fit

Use a CRD when the object is naturally part of cluster desired state, benefits from Kubernetes API conventions, should be watched/reconciled, and can use Kubernetes storage semantics. Avoid CRDs as general-purpose application data stores, high-write telemetry stores, or as a substitute for a domain database.

Design smell: “giant spec”

If one CRD contains dozens of unrelated subsystems, unbounded free-form maps and deeply coupled state machines, consider decomposing the API. Good Kubernetes APIs tend to expose cohesive resources with clear ownership.

13. Knowledge check

1. Does installing a CRD automatically create a controller?
No. It registers a custom API type. Behavior requires a controller/operator or other external actor.
2. Why is exactly one CRD version marked storage: true?
Kubernetes needs a canonical persisted representation for the custom resource in storage.
3. What is the difference between served and storage?
served controls client availability of a version. storage identifies the version persisted by the API server.
4. Why separate spec and status?
spec expresses desired state; status reports observed state. The status subresource helps enforce that ownership separation.
5. Why can a deleted CR remain in Terminating?
A finalizer can block removal until its responsible controller completes cleanup and removes the finalizer.
6. What should you check when a field vanishes after applying a custom resource?
Whether that field exists in the CRD structural schema; undeclared fields can be pruned.
7. When is a conversion webhook needed?
When different served versions require semantic field/data transformation rather than a simple version-label change.
8. Why should you not store routine application records in CRDs?
They consume Kubernetes API/etcd capacity and couple normal application data-plane operation to the control-plane API.
