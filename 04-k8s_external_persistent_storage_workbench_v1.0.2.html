4.1 Storage Concepts Recap

Ephemeral storage

  • Lives with the Pod or container lifecycle.
  • Example: emptyDir.
  • Useful for cache, scratch files and temporary processing.
  • Deleting and recreating the Pod normally removes the data.

Persistent storage

  • Has a lifecycle independent from an individual Pod.
  • Applications request it through a PVC.
  • The claim binds to a PV.
  • A CSI driver connects Kubernetes to the real storage backend.
Simple analogy: Pod = hotel guest, PVC = room request, PV = assigned room, StorageClass = room category, CSI driver = hotel operations team, storage backend = the actual building and rooms.

CSI — Container Storage Interface

  • CSI is a standard interface that lets storage vendors integrate with Kubernetes without putting vendor-specific storage code inside Kubernetes core.
  • The external provisioner watches PVCs and asks the CSI driver to create storage when dynamic provisioning is required.
  • The attacher coordinates attachment for attachable volumes.
  • The node plugin performs node-side staging and mounting.
  • The resizer handles PVC growth for supported CSI drivers.

Real-world use case: A database Deployment can be rescheduled to another node while its data remains represented by the same PVC/PV relationship. The CSI driver handles the storage operations needed to make that persistent volume usable by the new Pod location.

4.2 StorageClass — deep dive

A StorageClass is a cluster-scoped policy object describing how storage should be provisioned.

FieldMeaningLearning point
provisionerCSI/external provisioner identity.Longhorn uses driver.longhorn.io.
parametersDriver-specific settings.Example: replica count, filesystem type.
reclaimPolicyWhat happens to dynamically provisioned PVs after claim deletion.Delete or Retain.
allowVolumeExpansionWhether a bound PVC may request a larger capacity.Growth only; Kubernetes does not shrink PVC storage.
volumeBindingModeWhen provisioning/binding occurs.Immediate or WaitForFirstConsumer.

Immediate

  • Provisioning/binding starts when the PVC is created.
  • Simple and fast.
  • May choose storage before the scheduler knows where the consuming Pod will run.

WaitForFirstConsumer

  • PVC waits until a Pod actually references it.
  • Scheduler context becomes available first.
  • Useful for topology-constrained storage.

4.3 PersistentVolumes (PV)

  • A PV is a cluster-scoped storage resource.
  • It can be created statically by an administrator or dynamically from a StorageClass.
  • Its lifecycle is independent of a Pod.

Access modes

ModeMeaningImportant nuance
RWOReadWriteOnceRead-write by one node; multiple Pods on that same node may still use it.
ROXReadOnlyManyRead-only by many nodes; support depends on the driver. Longhorn does not advertise ROX as a supported mode.
RWXReadWriteManyRead-write by many nodes. Longhorn provides RWX using a share-manager/NFS path.
RWOPReadWriteOncePodSingle Pod across the cluster; strongest Kubernetes single-Pod access guarantee for supported CSI volumes.

PV lifecycle phases

4.4 PersistentVolumeClaims (PVC)

  • A PVC is a namespaced request for storage.
  • The control plane looks for a compatible PV or asks a dynamic provisioner to create one.
  • PV↔PVC binding is exclusive and one-to-one.
  • For static matching, Kubernetes evaluates storage class, requested capacity, access modes, volume mode and any selector constraints.
  • A PVC may pre-bind to a specific PV with volumeName.
Binding rule: a claim can receive a PV that is larger than requested, but it cannot bind to a PV that is smaller than the request.
Subtle but important: storageClassName: "" means “no StorageClass”. Omitting storageClassName can allow the default StorageClass mechanism to assign one.

Real-world storage patterns

Database growth

  • Start a database with a moderate PVC.
  • Enable expansion in its StorageClass.
  • Grow the PVC online as usage increases.

Multi-node shared content

  • Use RWX when multiple nodes need shared read/write files.
  • Examples: shared uploads, build artifacts, collaborative file workloads.
  • Validate backend-specific RWX behavior and performance.

Data protection on deletion

  • Use Retain where accidental claim deletion must not erase data.
  • Examples: migration staging, regulated data, manual recovery workflows.
  • Pair with backup policy; Retain is not a backup.

Topology-constrained storage

  • Use WFFC so scheduling context is known before provisioning.
  • Useful when storage is limited to zones, racks or specific nodes.

Legacy/static capacity

  • Admin creates the PV first.
  • Useful for imported disks, pre-existing NFS exports or controlled migration volumes.

Disposable application state

  • Use ephemeral volumes for cache and scratch work.
  • Do not put business-critical state into emptyDir.

0C. Recommended automated preflight

Important prerequisite: longhornctl check preflight uses the longhorn-system namespace. On a fresh cluster, create the namespace before running the checker. Creating this namespace does not install Longhorn.
bash · admin workstation
export LH_VERSION=1.12.1

# Detect the architecture of the machine running longhornctl.
case "$(uname -m)" in
  x86_64)  export ARCH=amd64 ;;
  aarch64) export ARCH=arm64 ;;
  *)
    echo "STOP: unsupported admin-host architecture: $(uname -m)"
    exit 1
    ;;
esac

export LH_BIN="longhornctl-linux-${ARCH}"
export LH_URL="https://github.com/longhorn/cli/releases/download/v${LH_VERSION}"

echo "Longhorn CLI version: ${LH_VERSION}"
echo "Admin-host architecture: ${ARCH}"

# Create/verify the namespace idempotently BEFORE preflight.
kubectl create namespace longhorn-system \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl get namespace longhorn-system

# Download the CLI and its published checksum.
curl -fLO "${LH_URL}/${LH_BIN}"
curl -fLO "${LH_URL}/${LH_BIN}.sha256"

# Verify the binary BEFORE executing it.
sha256sum -c "${LH_BIN}.sha256"
chmod +x "${LH_BIN}"
mv -f "${LH_BIN}" longhornctl

./longhornctl version
./longhornctl check preflight
Expected: checksum verification returns OK, the longhorn-system namespace is Active, and each Kubernetes node passes the Longhorn host prerequisite checks.
If you previously saw: Failed to run preflight checker: namespaces "longhorn-system" not found — it means the checker had no namespace in which to create its temporary resources. The idempotent namespace command above fixes that condition.

6A. RWO — one node, not necessarily one Pod

  • A RWO Longhorn volume can be mounted read-write by one node.
  • Do not teach RWO as “exactly one Pod”. That statement is incorrect.
