Module 2 · Kubernetes Identity & Access

Who — or what — is allowed to talk to your cluster?

Every request that reaches the Kubernetes API server — a human running kubectl, a controller, or a process inside a Pod — carries an identity. This module builds that identity model from the ground up: how the cluster tells identities apart, why the default identity every Pod gets is a real security liability, and how to hand each workload exactly the access it needs and nothing more.

Target environment3-node kubeadm cluster
Format8 concept sections + 5 labs
Estimated time~2 hours
Prerequisiteskubectl configured, cluster-admin context
Every request — human or Pod — passes through the same three gates before it ever touches cluster state.
Orientation

Kubernetes authentication, at a glance

The API server doesn't maintain a login system. Instead it delegates the question "who is this?" to a chain of pluggable authenticator modules, then hands the result to authorization and admission control. Nothing gets into etcd without clearing all three gates.

STAGE 1

Authentication

Identifies the caller. Methods include x509 client certificates, bearer tokens (ServiceAccount tokens, OIDC), and webhook authenticators. Produces a username and group list — or rejects the request outright (401).

STAGE 2

Authorization

Decides if that identity may perform this verb on this resource. RBAC is the default and near-universal mechanism in modern clusters. A clean pass here is required, or the request is denied (403).

STAGE 3

Admission control

Mutating and validating webhooks/plugins get a last look — injecting defaults, enforcing policy — before the object is ever persisted. Out of scope for this module, but it's why "authorized" isn't always "accepted."

Real-world framing: a CI/CD runner deploying a Helm chart, a Prometheus Pod scraping metrics via the API, and you running kubectl get pods from your laptop all hit the exact same pipeline. The cluster doesn't have a special case for "automated" traffic — it just has identities with different scopes of access.

2.1 · Users vs Service Accounts

Users vs ServiceAccounts

Kubernetes recognizes two categories of identity for API requests, and only one of them is actually a Kubernetes object.

Users

External / human identity
  • Object in etcd? No — Kubernetes has no User API resource
  • Issued by An external system: a CA, your cloud provider's IAM, or an OIDC/SSO provider
  • Presented as An x509 cert (CN = username, O = groups) or an OIDC bearer token
  • Typical lifetime Days to years — tied to cert/token expiry, not to anything in-cluster
  • Real-world use Platform engineers running kubectl, admins using a dashboard, SSO-federated developer access

ServiceAccounts

In-cluster / workload identity
  • Object in etcd? Yes — kubectl get serviceaccounts lists real, namespaced objects
  • Issued by The cluster itself, via the ServiceAccount and TokenRequest controllers
  • Presented as A signed JWT bearer token, automatically projected into the Pod's filesystem
  • Typical lifetime Short — bound tokens default to ~1 hour and auto-rotate
  • Real-world use A controller watching resources, a CI pipeline Pod deploying manifests, a sidecar calling the API

2.1 · Users vs Service Accounts

Default ServiceAccount behavior — and why it's a risk

Every namespace gets a ServiceAccount named default the moment it's created — nobody asks for it. Every Pod that doesn't explicitly request a different one is silently assigned it.

Implicit propagation: the default ServiceAccount is mounted into any Pod that doesn't specify one.

Where the risk actually comes from

A brand-new default ServiceAccount has no RBAC bound to it, so on its own it can do almost nothing. The danger appears later — when someone binds a Role, ClusterRole, or (worse) cluster-admin to default for convenience, or to the system:serviceaccounts group as a whole.

Why it matters in practice

If an application Pod is compromised — a dependency vulnerability, an SSRF bug, a leaked shell — the attacker inherits whatever the Pod's mounted token can do. If that token belongs to an over-privileged default SA, a single app bug becomes a path to the wider cluster.

This is a CIS Kubernetes Benchmark control for a reason. The recommended baseline is: never bind RBAC to a namespace's default ServiceAccount, disable its automount, and give every real workload its own narrowly-scoped identity instead. Lab 1 shows exactly what a compromised Pod can see using nothing but its default credential.

2.2 · Service Accounts — In Depth

ServiceAccount tokens

A ServiceAccount's credential is a signed JSON Web Token (JWT). Since Kubernetes 1.24, the projected, time-bound token is the default — a meaningful security upgrade over the long-lived tokens older clusters used.

A ServiceAccount token is a standard JWT: three base64url segments joined by dots, anyone can read the middle segment — only the API server can verify the signature.
DEFAULT SINCE 1.24

Bound / projected tokens

Requested via the TokenRequest API, mounted as a projected volume by the kubelet. Carries an aud (audience) claim scoped to the API server, an exp claim (default ~1 hour), and can be tied to the specific Pod's UID — steal it, and it stops working once that Pod is gone.

LEGACY, PRE-1.24 DEFAULT

Secret-backed tokens

A kubernetes.io/service-account-token Secret auto-created per ServiceAccount, with no expiry at all. Still creatable manually for legacy integrations, but no longer the default — and every long-lived token is a standing liability sitting in etcd.

2.2 · Service Accounts — In Depth

Pod-to-Kubernetes API authentication

How does code inside a container actually become an authenticated API caller? The kubelet does the work before the container ever starts.

1 · MOUNT

Projected volume

The kubelet mounts token, ca.crt, and namespace at /var/run/secrets/kubernetes.io/serviceaccount/ — no manifest changes needed, it's automatic for any Pod with a mounted SA.

2 · DISCOVER

In-cluster config

Client libraries (client-go, client-python, …) auto-detect these files plus KUBERNETES_SERVICE_HOST/_PORT env vars — no kubeconfig, no hardcoded endpoint.

3 · CALL

Authenticated request

The token is sent as Authorization: Bearer <token>, validated against ca.crt for TLS trust — the exact same pipeline a human's kubectl request goes through.

Real-world use case: this is exactly how a Prometheus Pod discovers scrape targets via the API, how an Argo CD controller applies manifests, and how a Kubernetes Operator watches its custom resources — all without a single hardcoded credential in the container image.

2.2 · Service Accounts — In Depth

Auto-mounting tokens and security implications

Token projection is automatic by default — which is convenient for workloads that need it, and an unnecessary attack surface for the ones that don't.

SettingSet atEffect
automountServiceAccountToken: falseServiceAccountNo Pod using this SA gets a token mounted, unless a Pod overrides it explicitly
automountServiceAccountToken: truePod specOverrides the ServiceAccount setting — this specific Pod gets a token regardless
Neither set—Defaults to true — a token is mounted

Baseline practice: set automountServiceAccountToken: false on every namespace's default SA. Then opt back in per-Pod, only for workloads that genuinely call the Kubernetes API. Most application Pods — a web frontend, a stateless API, a batch job that only talks to a database — never need cluster credentials at all.

2.2 · Service Accounts — In Depth

ServiceAccount-per-workload best practice

One shared identity for every Pod in a namespace is convenient to set up and expensive to audit. Give each workload its own.

Same four workloads, two identity models — one gives you an audit trail worth reading.

Why it pays off

Blast-radius containment, clean audit trails (system:serviceaccount:ns:checkout-sa in every log line beats a generic default), and RBAC that can actually be scoped per-app instead of per-namespace.

Real-world pattern

A microservices platform typically has one SA per Deployment — logging-agent-sa can only read/write log-related resources, payment-service-sa can only reach its own Secrets and ConfigMaps, and nothing overlaps by accident.

2.2 · Service Accounts — In Depth

Least-privilege access for applications

A ServiceAccount is just an identity — it has zero permissions until RBAC says otherwise. Least privilege means granting the smallest set of verbs, on the smallest set of resources, at the smallest scope that the workload actually needs.

The chain that turns "an identity exists" into "this identity may do exactly this."

Role & ClusterRole

A Role grants access within one namespace. A ClusterRole can grant cluster-wide access, or be reused across namespaces via multiple RoleBindings. Default to Role unless you have a concrete reason to go cluster-wide.

Scope down to subresources

RBAC can grant pods/log without granting pods itself, or pods/exec separately from either. A log shipper never needs to read full Pod specs — grant the subresource, not the object.

Verify before you ship: kubectl auth can-i <verb> <resource> --as=system:serviceaccount:<ns>:<name> -n <ns> answers "yes" or "no" using the real RBAC evaluation — no need to spin up a Pod just to test a permission. Every lab below uses it as the standard verification step.

Lab 1 · What the default ServiceAccount exposes

Launch a Pod with no ServiceAccount set, find its mounted credential, and use it to call the API server directly — seeing exactly what a compromised Pod inherits by default.

Intro~20 min
Prerequisite: iam-lab namespace exists (created above). No ServiceAccounts or RBAC objects yet.
1

Launch a Pod with no ServiceAccount specified

We use curlimages/curl rather than plain busybox — its curl negotiates TLS against the API server properly, where busybox's minimal wget TLS stack often fails the handshake outright.

test-pod.yaml
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: test-pod
  namespace: iam-lab
spec:
  containers:
  - name: app
    image: curlimages/curl:8.10.1
    command: ["sleep", "3600"]
EOF
kubectl wait --for=condition=Ready pod/test-pod -n iam-lab --timeout=60s
2

Confirm which ServiceAccount it actually got

bash
kubectl get pod test-pod -n iam-lab -o jsonpath='{.spec.serviceAccountName}{"\n"}'
EXPECTED OUTPUT
default
3

Find the auto-mounted credential inside the Pod

bash
kubectl exec -n iam-lab test-pod -- ls /var/run/secrets/kubernetes.io/serviceaccount/
EXPECTED OUTPUT
ca.crt
namespace
token
4

Pull the token out and inspect its claims

Copy the token into a shell variable, then decode the JWT payload with Python (handles base64url padding correctly, unlike a raw base64 -d).

bash
TOKEN=$(kubectl exec -n iam-lab test-pod -- cat /var/run/secrets/kubernetes.io/serviceaccount/token)

python3 -c "
import base64, json
payload = '$TOKEN'.split('.')[1]
payload += '=' * (-len(payload) % 4)
print(json.dumps(json.loads(base64.urlsafe_b64decode(payload)), indent=2))
"
EXPECTED OUTPUT (abridged)
{
  "aud": ["https://kubernetes.default.svc"],
  "exp": 1234567890,
  "kubernetes.io": {
    "namespace": "iam-lab",
    "pod": {"name": "test-pod", ...},
    "serviceaccount": {"name": "default", ...}
  },
  "sub": "system:serviceaccount:iam-lab:default"
}

Note the exp claim — this is a bound token, valid for roughly an hour, not the indefinitely-lived kind older clusters issued by default.

5

Use the token to make a real, authenticated API call — from inside the Pod

This is the credential in use, exactly as an attacker with shell access to this Pod would use it.

bash
kubectl exec -n iam-lab test-pod -- sh -c '
curl -sS \
  --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
  --header "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  https://kubernetes.default.svc/api'
EXPECTED OUTPUT
{
  "kind": "APIVersions",
  "versions": ["v1"],
  ...
}
6

Now try something that requires actual RBAC permission

bash
kubectl exec -n iam-lab test-pod -- sh -c '
curl -sS \
  --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
  --header "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  https://kubernetes.default.svc/api/v1/namespaces/iam-lab/pods'
EXPECTED OUTPUT
{
  "kind": "Status",
  "apiVersion": "v1",
  "status": "Failure",
  "message": "pods is forbidden: User \"system:serviceaccount:iam-lab:default\" cannot list resource \"pods\" in API group \"\" in the namespace \"iam-lab\"",
  "reason": "Forbidden",
  "code": 403
}
Verify & key learnings
  • Step 5 succeeded and step 6 failed — the token authenticates fine (identity is valid), it's authorization that currently blocks it. A fresh default SA has no RBAC bound, which is exactly the safe starting point.
  • The risk isn't the token existing — it's what happens the day someone binds a Role or cluster-admin to default for convenience. Every Pod in the namespace inherits that instantly.
  • Leave test-pod running — Lab 2 uses it for comparison.

Lab 2 · Give the workload its own identity, and control automount

Create a dedicated ServiceAccount, disable automount on the namespace's default SA, and confirm the difference in what each Pod ends up with.

Core~20 min
Prerequisite: Lab 1 complete, test-pod still running in iam-lab.
1

Create a dedicated ServiceAccount

bash
kubectl create serviceaccount app-reader-sa -n iam-lab
2

Disable automount on the namespace's default SA

This is the safe-by-default hardening step: unlabeled Pods stop getting a live API credential at all.

bash
kubectl patch serviceaccount default -n iam-lab \
  -p '{"automountServiceAccountToken": false}'
3

Launch a Pod explicitly using the new ServiceAccount

app-pod.yaml
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
  namespace: iam-lab
spec:
  serviceAccountName: app-reader-sa
  automountServiceAccountToken: true
  containers:
  - name: app
    image: curlimages/curl:8.10.1
    command: ["sleep", "3600"]
EOF
kubectl wait --for=condition=Ready pod/app-pod -n iam-lab --timeout=60s
4

Confirm a fresh default-SA Pod now gets no token at all

bash
kubectl run no-token-pod --image=busybox:1.36 -n iam-lab --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/no-token-pod -n iam-lab --timeout=60s
kubectl exec -n iam-lab no-token-pod -- ls /var/run/secrets/kubernetes.io/serviceaccount/
EXPECTED OUTPUT
ls: /var/run/secrets/kubernetes.io/serviceaccount/: No such file or directory
Verify & key learnings
  • app-pod (explicit SA + automountServiceAccountToken: true) has a token. no-token-pod (default SA, automount now disabled) does not — the Pod-level setting overrides the ServiceAccount-level one, and here neither Pod set an override, so the SA-level default wins.
  • test-pod from Lab 1 keeps its original token — the automount setting only affects Pods created after the patch.
  • This is the pattern: deny by default at the ServiceAccount, opt in explicitly per Pod that genuinely needs API access.

Lab 3 · Bind least-privilege RBAC to the ServiceAccount

Grant app-reader-sa permission to read Pods — and nothing more — using a Role and RoleBinding, then prove the boundary with kubectl auth can-i.

Core~25 min
Prerequisite: Lab 2 complete — app-reader-sa and app-pod exist in iam-lab.
1

Confirm the ServiceAccount currently has zero permissions

bash
kubectl auth can-i list pods \
  --as=system:serviceaccount:iam-lab:app-reader-sa -n iam-lab
EXPECTED OUTPUT
no
2

Create a Role scoped to read-only Pod access

pod-reader-role.yaml
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: iam-lab
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
EOF
3

Bind the Role to the ServiceAccount

pod-reader-binding.yaml
cat <<EOF | kubectl apply -f -
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-reader-binding
  namespace: iam-lab
subjects:
- kind: ServiceAccount
  name: app-reader-sa
  namespace: iam-lab
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
EOF
4

Verify the boundary — allowed and denied actions

bash
kubectl auth can-i list pods \
  --as=system:serviceaccount:iam-lab:app-reader-sa -n iam-lab
kubectl auth can-i delete pods \
  --as=system:serviceaccount:iam-lab:app-reader-sa -n iam-lab
kubectl auth can-i list pods \
  --as=system:serviceaccount:iam-lab:app-reader-sa -n default
EXPECTED OUTPUT
yes
no
no
5

Confirm it live, from inside the Pod itself

bash
kubectl exec -n iam-lab app-pod -- sh -c '
curl -sS \
  --cacert /var/run/secrets/kubernetes.io/serviceaccount/ca.crt \
  --header "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  https://kubernetes.default.svc/api/v1/namespaces/iam-lab/pods | head -c 200'
EXPECTED OUTPUT
{"kind":"PodList","apiVersion":"v1", ...
Verify & key learnings
  • The third can-i check (-n default) returning no confirms a Role's grant stays inside its own namespace — that's the difference from a ClusterRole.
  • kubectl auth can-i --as= is the fast way to validate RBAC before you ever run a workload — prefer it over trial-and-error from inside a Pod.
  • The Role grants three read verbs on one resource — nothing about Secrets, Deployments, or write access was ever in scope.

Lab 4 · Bound tokens vs legacy long-lived tokens

Issue a short-lived token via the TokenRequest API, inspect its claims, then create an old-style Secret-backed token and compare the two side by side.

Advanced~25 min
Prerequisite: Lab 3 complete — app-reader-sa exists with RBAC bound.
1

Request a bound token directly with kubectl create token

This calls the TokenRequest API — the same mechanism the kubelet uses to project tokens into Pods.

bash
kubectl create token app-reader-sa -n iam-lab --duration=10m
EXPECTED OUTPUT
eyJhbGciOiJSUzI1NiIsImtpZCI6Ii4uLiJ9.eyJhdWQiOlsi... (a JWT string)
2

Decode it and check the expiry window

bash
SHORT_TOKEN=$(kubectl create token app-reader-sa -n iam-lab --duration=10m)

python3 -c "
import base64, json, time
payload = '$SHORT_TOKEN'.split('.')[1]
payload += '=' * (-len(payload) % 4)
claims = json.loads(base64.urlsafe_b64decode(payload))
print('exp:', claims['exp'], '  seconds from now:', claims['exp'] - int(time.time()))
print('aud:', claims['aud'])
"
EXPECTED OUTPUT
exp: 1234568490   seconds from now: ~600
aud: ['https://kubernetes.default.svc']
3

Now create a legacy, Secret-backed token for comparison

Pre-1.24 clusters auto-created one of these per ServiceAccount. Modern clusters don't — but the mechanism still exists for legacy integrations that can't use short-lived tokens.

legacy-token.yaml
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Secret
metadata:
  name: app-reader-legacy-token
  namespace: iam-lab
  annotations:
    kubernetes.io/service-account.name: app-reader-sa
type: kubernetes.io/service-account-token
EOF
kubectl wait --for=jsonpath='{.data.token}' secret/app-reader-legacy-token -n iam-lab --timeout=30s
4

Decode the legacy token's claims

bash
LEGACY_TOKEN=$(kubectl get secret app-reader-legacy-token -n iam-lab -o jsonpath='{.data.token}' | base64 -d)

python3 -c "
import base64, json
payload = '$LEGACY_TOKEN'.split('.')[1]
payload += '=' * (-len(payload) % 4)
claims = json.loads(base64.urlsafe_b64decode(payload))
print('has exp claim:', 'exp' in claims)
print('sub:', claims.get('sub'))
"
EXPECTED OUTPUT
has exp claim: False
sub: system:serviceaccount:iam-lab:app-reader-sa
5

Clean up the legacy token — don't leave long-lived credentials lying around

bash
kubectl delete secret app-reader-legacy-token -n iam-lab
Verify & key learnings
  • The bound token carries an exp claim roughly 10 minutes out (matching --duration); the legacy Secret-backed token has none at all — it's valid until someone manually revokes it.
  • Same ServiceAccount, same RBAC, two very different risk profiles depending on which token type is in use.
  • This is exactly why bound tokens became the 1.24 default: identical permissions, dramatically smaller time-window if one leaks.

Lab 5 · End-to-end: subresource scoping, negative testing, teardown

Build a log-reader workload scoped to exactly one subresource, confirm what it can and can't reach, then remove everything this module created in a single command.

Core~30 min
Prerequisite: Labs 1–4 complete. iam-lab namespace still has test-pod and app-pod running.
1

Create a log-producing Pod and a scoped ServiceAccount

Module recap: Users are external identities Kubernetes never stores; ServiceAccounts are real, namespaced objects meant for workloads. Every Pod gets one whether you ask for it or not, so the default should be locked down, not left open. Bound tokens replaced long-lived ones for a reason. Scope RBAC to the verb, resource, and subresource a workload actually needs — then verify it with kubectl auth can-i, not assumption.

Validated against a 3-node kubeadm cluster using busybox:1.36 (shells, log producers) and curlimages/curl:8.10.1 (any step that calls the API server over TLS) — no cloud-managed load balancers, no deprecated kubectl flags, no external images requiring authentication.
