Module 5 • Workload resilience

Pod Health
Management

Kubernetes can restart a container that is no longer healthy, and it can stop routing Service traffic to a Pod that is temporarily unable to serve. The critical skill is knowing which health signal should cause which action.

Audience: Kubernetes traineesDepth: concept → implementation Standalone referenceValidated against Kubernetes 1.37 docs
Series continuity

From traffic routing to backend health

The earlier ingress/traffic-management topic explained how external requests move through an Ingress or Gateway toward a Service and its Pods. This module focuses on the next question: should a selected Pod receive traffic, and should its container keep running?

Next in the learning path: combine probe health with Deployments, rollout strategy, PodDisruptionBudgets, resource limits, and observability.

One-sentence rule

Liveness decides restart. Readiness decides traffic eligibility. Startup protects slow initialization.

Foundation

Build the correct mental model first

Prerequisite check: this section assumes you already know what a Pod, container, Service, kubelet, and label selector are. If “Service selects Pods using labels” is unfamiliar, review Service fundamentals before the readiness lab.
Liveness

“Should I restart it?”

Detects a container that is running but no longer making useful progress: deadlock, stuck worker loop, unrecoverable internal state.

Readiness

“Should I send it traffic?”

Detects temporary inability to serve: cache warming, backend unavailable, draining, overloaded dependency, synchronization in progress.

Startup

“Has startup finished?”

Gives slow-starting applications a dedicated grace window before liveness/readiness checks take over.

5.1 Liveness probes

Detect “running but broken” containers

Important: a liveness probe should answer whether a restart is likely to recover the process. If a dependency outage will not be fixed by restarting your container, that dependency usually does not belong in liveness.

Exec probe

The kubelet runs a command inside the container. Exit status 0 means success; non-zero means failure. This is useful when health can be evaluated locally without exposing a network endpoint.

YAML — exec liveness
livenessProbe:
  exec:
    command:
      - /bin/sh
      - -c
      - test -f /tmp/healthy
  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 1
  failureThreshold: 3

Avoid expensive commands. Probe execution itself consumes container CPU and can become misleading under resource pressure.

HTTP GET probe

The kubelet sends an HTTP request to the Pod. HTTP status codes from 200 through 399 count as success; other responses count as failure.

YAML — HTTP liveness
livenessProbe:
  httpGet:
    path: /livez
    port: http
    scheme: HTTP
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

Prefer a lightweight, application-owned health path. Do not make /livez perform a deep database query on every probe.

TCP socket probe

The kubelet attempts to establish a TCP connection to the configured port. Connection established = success. It proves that something is accepting TCP connections, not that the application is semantically healthy.

YAML — TCP liveness
livenessProbe:
  tcpSocket:
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
  timeoutSeconds: 1
  failureThreshold: 3
ProbeBest whenBlind spot
ExecHealth is local and command-basedCommand can be expensive or depend on shell/tools not present

TCPYou only need to know whether a listener accepts connectionsA hung app may still accept TCP
Failure thresholds and timing

Probe timing is a control system

Probe timing determines how quickly Kubernetes reacts and how tolerant it is of transient failures. Aggressive settings shorten detection time but increase false positives.

FieldMeaning
initialDelaySecondsWait before the first probe begins (unless a startup probe is used to gate it).
periodSecondsHow often to probe.
timeoutSecondsHow long one attempt may take before failure.
failureThresholdConsecutive failures before Kubernetes takes failure action.
successThresholdConsecutive successes required after failure; for liveness/startup it must be 1.

Approximate detection window

For a steady failure after probing starts, a useful mental estimate is approximately:

failureThreshold × periodSeconds

This is an estimate rather than a hard SLA: scheduling, timeout behavior, probe execution time, and when the failure begins relative to the probe cycle affect exact timing.

Operational safety

Common misconfigurations and why they hurt

1. Liveness checks an external dependency

If the database is down, every app replica may fail liveness and restart simultaneously. The restart does not repair the database and can amplify the incident.

Better: keep liveness local; use readiness for “cannot serve right now.”

2. Probe begins before slow startup completes

The container enters a restart loop even though it would eventually initialize.

Better: use startupProbe for a distinct startup grace budget.

3. Probe path lies

/health always returns 200 even when request handling is broken, or performs no meaningful application check.

Better: define explicit semantics for /livez and /readyz.

4. Timing is too aggressive

CPU pressure or a brief pause causes false failures and restart storms.

Better: base thresholds on observed startup/runtime behavior and SLOs.

5. Readiness and liveness are identical by habit

A temporary inability to serve becomes an unnecessary restart.

Better: design each probe around its control action.

6. TCP chosen for an HTTP-level failure

The socket accepts connections while every HTTP request returns 500, so the probe continues to pass.

Better: use HTTP if application-level semantics matter.

5.2 Readiness probes

Traffic eligibility without killing the process

A readiness probe runs throughout the container lifecycle. When readiness fails, the Pod becomes unready and should not receive ordinary traffic through Kubernetes Services. The container is not restarted merely because readiness failed.

Readiness

Good questions

Has required in-memory state loaded?
Can this replica safely accept new requests?
Is this instance intentionally draining?
Is a critical dependency currently required for serving?
Liveness

Good questions

Is the main process deadlocked?
Has an unrecoverable local condition occurred?
Would restarting this container likely restore progress?

Notice the wording: liveness asks about recoverability via restart, not just “is anything wrong?”

BehaviorLiveness failureReadiness failure
Container restarted?Yes, after configured failure threshold, subject to restart policyNo
Pod can receive Service traffic?Not directly the purposeNo ordinary Service traffic while unready
Runs through lifecycle?Yes, after startup gatingYes, after startup gating
Main useRecover stuck processTemporarily withdraw from load balancing
Readiness → Service backends

What actually changes when a Pod becomes unready?

Earlier concept required: Services and label selectors. A Service does not “discover readiness” by itself; Kubernetes control-plane components maintain backend endpoint information, represented today by EndpointSlice objects.
Observe modern Service backend readiness
kubectl get pods -o wide
kubectl get endpointslices -l kubernetes.io/service-name=web -o yaml

# Focus on readiness conditions:
kubectl get endpointslices \
  -l kubernetes.io/service-name=web \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}'

The legacy Endpoints API is deprecated in current Kubernetes; use EndpointSlice for modern troubleshooting and tooling.

Startup probes

Give slow applications a separate startup budget

When a startupProbe is configured, liveness and readiness checks do not take over until startup succeeds. This avoids inflating liveness delays merely to accommodate rare or slow initialization.

Example: 5-minute startup budget

YAML
startupProbe:
  httpGet:
    path: /healthz
    port: http
  periodSeconds: 10
  failureThreshold: 30   # 30 × 10s = 300s

livenessProbe:
  httpGet:
    path: /livez
    port: http
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /readyz
    port: http
  periodSeconds: 5
  failureThreshold: 2

Comparison

ProbeQuestionFailure action
StartupHas initialization completed?Restart after startup budget is exhausted
LivenessIs runtime progress recoverable?Restart
ReadinessCan this instance serve now?Withdraw traffic

A startup probe succeeds once and then gets out of the way; readiness and liveness continue afterward.

Production design

How to design health endpoints deliberately

/livez

Fast, local, conservative. It should fail only when restart is likely to improve health.

/readyz

May include dependencies that are necessary to serve requests. It can fail transiently without killing the container.

/startupz

Represents completion of one-time initialization, migrations, model loading, cache build, or warm-up.

Should readiness check a database?

Sometimes. If this replica cannot serve any meaningful request without the database, readiness can reflect database reachability. But do not make a shared dependency outage cause every replica to churn through liveness restarts. Also consider whether removing every Pod from Service endpoints during a dependency incident prevents useful degraded responses.

Should liveness use the same endpoint as readiness?

It can in simple applications, but it is often an architectural smell. The two probes answer different questions and trigger different actions. Separate endpoints make those semantics explicit.

What about gRPC?

Kubernetes supports native gRPC health probes when the application implements the gRPC Health Checking Protocol. This module focuses on the requested exec, HTTP, and TCP probes, but the same liveness/readiness/startup intent still applies.

Lab 1 — Exec liveness: observe an automatic restart

Goal: create a file-backed health signal, deliberately remove it, and verify that the kubelet restarts the container.

1
Create the Pod.
01-exec-liveness.yaml
cat > 01-exec-liveness.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: exec-live
spec:
  containers:
  - name: app
    image: registry.k8s.io/busybox:1.27.2
    command: ["/bin/sh","-c"]
    args:
      - touch /tmp/healthy;
        sleep 30;
        rm -f /tmp/healthy;
        sleep 600
    livenessProbe:
      exec:
        command: ["cat","/tmp/healthy"]
      initialDelaySeconds: 5
      periodSeconds: 5
      timeoutSeconds: 1
      failureThreshold: 3
EOF
kubectl apply -f 01-exec-liveness.yaml
2
Watch restart count.
Observe
kubectl get pod exec-live -w
# In another terminal:
kubectl describe pod exec-live

After the health file disappears and enough consecutive probes fail, RESTARTS increases. The Pod object stays; the container instance restarts.

3
Inspect evidence.
Events + previous container
kubectl get events --sort-by=.lastTimestamp | tail -n 20
kubectl logs exec-live --previous 2>/dev/null || true

Lab 3 — TCP liveness/readiness: prove what TCP can and cannot tell you

03-tcp-probes.yaml
cat > 03-tcp-probes.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: tcp-health
  labels:
    app: tcp-health

  containers:
  - name: app
    image: registry.k8s.io/goproxy:0.1
    ports:
    - containerPort: 8080

Lab 4 — Readiness removes a Pod from Service traffic

Goal: use an exec readiness gate that you can manually toggle, then observe the EndpointSlice condition.

1
Deployment + Service
cat > 04-readiness-service.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ready-web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ready-web
  template:
    metadata:
      labels:
        app: ready-web
    spec:
      containers:
      - name: web
        image: registry.k8s.io/e2e-test-images/agnhost:2.64.0
        args: ["netexec","--http-port=8080"]
        ports:
        - containerPort: 8080
        readinessProbe:
          exec:
            command: ["/bin/sh","-c","test -f /tmp/ready"]
          initialDelaySeconds: 2
          periodSeconds: 3
          failureThreshold: 1
        lifecycle:
          postStart:
            exec:
              command: ["/bin/sh","-c","touch /tmp/ready"]
---
apiVersion: v1
kind: Service
metadata:
  name: ready-web
spec:
  selector:
    app: ready-web
  ports:
  - port: 80
    targetPort: 8080
EOF
kubectl apply -f 04-readiness-service.yaml
kubectl rollout status deployment/ready-web
kubectl get pods -l app=ready-web -o wide
kubectl get endpointslices -l kubernetes.io/service-name=ready-web -o wide
2
Make one Pod unready.
Toggle readiness
POD=$(kubectl get pod -l app=ready-web -o jsonpath='{.items[0].metadata.name}')
echo "$POD"

kubectl exec "$POD" -- rm -f /tmp/ready
sleep 5

kubectl get pods -l app=ready-web
kubectl get endpointslices \
  -l kubernetes.io/service-name=ready-web \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}'

The targeted Pod should show 0/1 Ready, while its container continues running. EndpointSlice should reflect ready=false for that backend.

3
Restore readiness.
Restore
kubectl exec "$POD" -- touch /tmp/ready
sleep 5
kubectl get pods -l app=ready-web
kubectl get endpointslices \
  -l kubernetes.io/service-name=ready-web \
  -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}{" ready="}{.conditions.ready}{"\n"}{end}'

Lab 5 — Startup probe: protect deliberate slow initialization

Goal: demonstrate that liveness does not interfere until startup succeeds.

05-startup-probe.yaml
cat > 05-startup-probe.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: slow-start
spec:
  containers:
  - name: app
    image: registry.k8s.io/busybox:1.27.2
    command: ["/bin/sh","-c"]
    args:
      - sleep 25;
        touch /tmp/started /tmp/alive;
        sleep 3600
    startupProbe:
      exec:
        command: ["test","-f","/tmp/started"]
      periodSeconds: 5
      failureThreshold: 8
    livenessProbe:
      exec:
        command: ["test","-f","/tmp/alive"]
      periodSeconds: 5
      failureThreshold: 3
EOF
kubectl apply -f 05-startup-probe.yaml
kubectl get pod slow-start -w

The startup budget is about 8 × 5 = 40s, while the simulated initialization takes ~25s. After startup succeeds, liveness becomes relevant.

Troubleshooting

A repeatable probe debugging workflow

1. Inspect status and events

Commands
kubectl get pod POD -o wide
kubectl describe pod POD
kubectl get events --sort-by=.lastTimestamp | tail -n 30

2. Reproduce the probe manually

Exec examples
kubectl exec POD -- sh -c 'test -f /tmp/healthy; echo $?'
kubectl exec POD -- sh -c 'wget -qO- http://127.0.0.1:8080/healthz || true'

Manual localhost testing is useful, but remember the kubelet’s network path is not identical to “inside the container”.

3. Check restart evidence

Commands
kubectl get pod POD \
  -o jsonpath='{.status.containerStatuses[*].restartCount}{"\n"}'
kubectl logs POD --previous

4. Check readiness routing state

Commands
kubectl get pod POD -o jsonpath='{.status.conditions[?(@.type=="Ready")]}'
kubectl get endpointslices \
  -l kubernetes.io/service-name=SERVICE -o yaml
Symptom: Pod is Running but 0/1 Ready

Running describes container/process lifecycle. Ready describes traffic eligibility. Inspect the readiness probe, events, and EndpointSlice readiness condition.

Symptom: CrashLoopBackOff after adding a liveness probe

First suspect an incorrect probe path/port, a startup race, or thresholds that are too aggressive. Temporarily compare actual application startup time against your probe schedule. A startup probe is often the correct fix for legitimate long initialization.

Symptom: TCP probe succeeds but users still get HTTP 500

TCP only confirms that a connection can be established. Replace or supplement it with HTTP readiness/liveness if your failure mode requires application-level semantics.

Field summary

Keep these five rules

1. Liveness = restart decision

Fail it only for conditions where restarting the container is a reasonable recovery action.

2. Readiness = traffic decision

Fail it when the instance should temporarily stop receiving new Service traffic.

3. Startup = initialization protection

Use it instead of stretching liveness timing around slow startup.

4. Timing is engineering, not decoration

Set thresholds from actual startup latency, transient-failure tolerance, recovery objectives, and resource behavior.

5. Observe EndpointSlice

For readiness/service troubleshooting, inspect EndpointSlice readiness conditions rather than relying on the deprecated legacy Endpoints API.
