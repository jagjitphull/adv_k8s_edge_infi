3.1 Ingress Architecture

Ingress vs Service (LoadBalancer)

Both get outside traffic into your cluster. They solve it at different layers, and mixing them up is the single most common early design mistake.

A Service of type LoadBalancer exposes one app per external IP. An Ingress is a single entry point that routes many apps by host or path.
Definition
A Service (type: LoadBalancer) asks the cloud provider for one external IP wired straight to one Service. It works at L4 (TCP/UDP) — it forwards packets, it does not read HTTP paths, hostnames, or headers.
Definition
An Ingress is a set of L7 (HTTP/HTTPS) routing rules. It needs an Ingress Controller running in the cluster to actually enforce those rules — the Ingress object alone does nothing.
Service (LoadBalancer)Ingress
OSI layerL4 — TCP/UDPL7 — HTTP/HTTPS
Routing basisIP + port onlyHostname, path, headers
External IPs neededOne per ServiceOne, shared by every app
TLS terminationNot aware of it (pass-through only)Native — terminates at the controller
Cost on cloudOne LB per Service = one bill per ServiceOne LB in front of the Ingress controller = one bill total
On bare metalStays <pending> without MetalLBController exposed via NodePort or hostNetwork — no cloud dependency
Real-world use case
An e-commerce platform runs frontend, api, admin and checkout as separate microservices. With LoadBalancer Services that's 4 external IPs, 4 cloud LB bills, and 4 places to configure TLS. With one Ingress, it's one IP, one certificate, one set of routing rules — shop.site.com/, /api, /admin all point to different backends behind the same front door.

Role of the Ingress Controller

The Ingress resource is just a YAML wishlist. Something has to read it and actually configure a reverse proxy — that's the controller's job.

The controller is the missing piece between "I wrote a routing rule" and "traffic is actually routed."

Watches

Continuously watches the API server for Ingress, Service, Secret, and Endpoint changes relevant to it.

Translates

Converts Ingress rules into native reverse-proxy config — an nginx.conf block, a Traefik dynamic config, or a cloud ALB listener rule.

Reloads

Applies the new config with (ideally) zero dropped connections — this is what "hot reload" means for ingress-nginx.

Common mistake
Applying an Ingress manifest with no controller installed gives no error — kubectl apply succeeds because the object is valid YAML. Nothing tells you traffic isn't routing until you test it. Always confirm a controller Pod is Running first (Lab 1).

Common Ingress Controllers

The Ingress API is standard. What each controller does with it — and which annotations it understands — is not. This module installs NGINX live; Traefik and Cloud ALB are covered conceptually so you recognize them in the wild.

NGINX Ingress Live lab

The most widely deployed controller. Runs as Pods inside the cluster; config is annotation-driven.

  • Works identically on any cluster — cloud or bare metal
  • Huge annotation surface (rewrites, canary, rate limits, auth)
  • Maintained by the Kubernetes project itself

Traefik Conceptual

A Go-native reverse proxy with automatic service discovery and a strong Let's Encrypt integration story.

  • Config via IngressRoute CRDs, not just annotations
  • Built-in dashboard for live routing state
  • Popular in Docker-first shops migrating to k8s

Cloud ALB / GCE Conceptual

The cloud provider's own load balancer, driven directly by the Ingress object (AWS ALB Ingress Controller / GKE Ingress).

  • No proxy Pods to manage — the cloud runs it for you
  • Ties you to that cloud's LB feature set
  • Usually billed per-LB-hour + data processed
Real-world use case
A platform team standardizes on NGINX Ingress for portability — the same manifests work in their on-prem kubeadm cluster and their AWS EKS cluster. A team fully committed to AWS instead picks the ALB Ingress Controller to get native AWS WAF and Shield integration, accepting the trade-off of losing portability.

Path-based routing

One hostname, multiple applications — the URL path decides which Service receives the request.

Definition
Each path entry in an Ingress rule maps a URL prefix to a backend Service. The controller matches the incoming request path against these rules top-to-bottom (most specific match wins) and forwards accordingly.
Real-world use case
shop.techmart.local/ serves the storefront, /api serves the backend API, and /admin serves the internal admin panel — three different applications, three different teams, one domain and one certificate.

3Path-based routing across three apps

15 minhost: shop.techmart.local
Builds on: Lab 2's workloads. Verification uses port-forward + a Host header, so it works with no DNS and no /etc/hosts edit — the same method works on kubeadm, kind, or minikube.
1Create the path-based Ingress
pathType: Prefix matches the path and everything under it. The rewrite-target annotation strips the prefix before it reaches httpd/nginx, since those backends don't know they're mounted at /api or /admin.
techmart-path-ingress.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: techmart-path
  namespace: techmart
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
  - host: shop.techmart.local
    http:
      paths:
      - path: /()(.*)
        pathType: ImplementationSpecific
        backend: {service: {name: frontend-svc, port: {number: 80}}}
      - path: /api(/|$)(.*)
        pathType: ImplementationSpecific
        backend: {service: {name: api-svc, port: {number: 80}}}
      - path: /admin(/|$)(.*)
        pathType: ImplementationSpecific
        backend: {service: {name: admin-svc, port: {number: 80}}}
bash 
kubectl apply -f techmart-path-ingress.yaml
kubectl -n techmart get ingress techmart-path
EXPECTED OUTPUTNAME CLASS HOSTS ADDRESS PORTS AGE techmart-path nginx shop.techmart.local 80 5s

✓ KEY LEARNING
  • The Host header — not the URL you type — is what the Ingress controller matches against spec.rules[].host. That's why curl with -H "Host: ..." works with zero DNS setup
  • Regex capture groups + rewrite-target: /$2 is the standard NGINX-ingress pattern for stripping a path prefix — check this first whenever a routed app returns 404 for everything

Host-based routing

Instead of splitting by path, split by subdomain or domain entirely — each hostname gets its own rule block, potentially pointing at completely different backends and even different TLS certs.

Definition
A single Ingress (or several) can declare multiple host entries under spec.rules. The controller inspects the HTTP Host header (or SNI, for TLS) and picks the matching rule block — each host can have its own independent set of paths.
Real-world use case
shop.techmart.com and api.techmart.com are operated by different teams with different release cadences. Host-based routing lets each team own its Ingress object independently, while both still share the same controller, IP, and TLS cert infrastructure.

TLS termination

The Ingress controller decrypts HTTPS on the way in, so your Pods only ever speak plain HTTP internally — one certificate, managed in one place, instead of TLS configured inside every app.

TLS terminates at the Ingress controller. Traffic inside the cluster is plain HTTP unless you separately configure end-to-end TLS.
Real-world use case
A retailer renews one wildcard certificate for *.techmart.com and attaches it to the Ingress once. Every new microservice that adds a path or host to that Ingress is HTTPS-protected automatically — no per-app cert management, no expired-cert incidents traced to one forgotten service.

Annotations and controller-specific behavior

The Ingress spec is a small, stable API on purpose. Everything controller-specific — rewrites, timeouts, body size limits, canary weights — lives in metadata.annotations instead, which is why annotations are never portable between controllers.

Why this matters
An annotation prefixed nginx.ingress.kubernetes.io/... is silently ignored by Traefik or an ALB controller — no error, no warning, the behavior just doesn't happen. Always check which controller (ingressClassName) an annotation actually belongs to.
Annotation (nginx.ingress.kubernetes.io/...)PurposeExample
rewrite-targetRewrite the matched path before forwarding to the backend/$2
ssl-redirectForce HTTP → HTTPS redirect"true"
proxy-body-sizeMax upload size accepted before 413"50m"
proxy-read-timeoutSeconds to wait for a slow backend response"60"
configuration-snippetRaw NGINX config injection — powerful, high blast-radius, use sparinglycustom headers
canaryMarks this Ingress as a canary split (Lab 7)"true"
canary-weightPercentage of traffic sent to the canary backend"20"

6Apply and observe annotation-driven behavior

2Prove the limit is enforced

Blue/Green and Canary deployments

Two different answers to the same question: how do I ship a new version without an all-or-nothing cutover?

Canary Lab 7

Send a small, controlled percentage of traffic to the new version while most traffic stays on the old one. Increase the percentage gradually as confidence grows.

  • Real production traffic tests the new version, but blast radius is capped by the weight
  • Done via a second Ingress object with canary annotations

Blue/Green Lab 8

Run old ("blue") and new ("green") versions fully side by side, then cut over all traffic at once by repointing a Service selector.

  • Instant full cutover, and an equally instant full rollback
  • No partial-traffic state to reason about — it's either 100% blue or 100% green
Real-world use case
A payments API uses blue/green — correctness bugs in payment processing are unacceptable even for 5% of traffic, so the team wants full confidence before any customer request hits the new version, with an instant rollback path. The storefront's recommendation engine uses canary instead — a bad model update degrades UX for some users, not payments, so gradually testing on 10% of live traffic before a full rollout is an acceptable and much faster way to validate.

7Canary deployment — shift 20% of API traffic to v2

20 minAnnotation-based — no service mesh needed
Builds on: Lab 3's techmart-path (the "stable" Ingress, already routing /api to api-svc → api-v1/blue).
1Create a second Ingress marked as canary, same host + path, pointing at api-v2-svc
The canary Ingress must match the same host and path as the stable Ingress — the canary annotations are what tell ingress-nginx to treat it as a weighted split rather than a conflict.
techmart-canary-ingress.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: techmart-api-canary
  namespace: techmart
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20"
spec:
  ingressClassName: nginx
  rules:
  - host: shop.techmart.local
    http:
      paths:
      - path: /api(/|$)(.*)
        pathType: ImplementationSpecific
        backend: {service: {name: api-v2-svc, port: {number: 80}}}
bash 
kubectl apply -f techmart-canary-ingress.yaml
2Send 50 requests and count how many landed on each version
bash 
for i in $(seq 1 50); do
  curl -s -H "Host: shop.techmart.local" http://localhost:8080/api
done | sort | uniq -c
EXPECTED OUTPUT (approximate — weighting is probabilistic, not exact) 40 <h1>API v1</h1><p>served by api-v1 (blue)</p> 10 <h1>API v2</h1><p>served by api-v2 (green / canary)</p>
~80/20 split, matching canary-weight: "20". Small sample sizes will vary — this is expected of weighted random routing, not a bug.
3Promote — raise the weight, then remove the canary once at 100%
bash 
kubectl -n techmart annotate ingress techmart-api-canary \
  nginx.ingress.kubernetes.io/canary-weight="50" --overwrite
# once confident, cut the stable Ingress over to api-v2-svc directly, then:
kubectl -n techmart delete ingress techmart-api-canary
✓ KEY LEARNING
  • Canary is implemented as a second Ingress object, not a field on the original — the annotations on the canary Ingress are what make ingress-nginx treat the pair as one weighted route instead of two conflicting rules
  • Weight-based canary is approximate by design (it's random per-request, not sticky), which is fine for most APIs but wrong for anything needing session affinity — that needs canary-by-cookie or canary-by-header instead

10 minZero Ingress changes
Builds on: Lab 2's api-svc, currently selecting version: blue (api-v1).
1Confirm current state — api-svc is pointed at blue
bash

EXPECTED OUTPUT{"app":"api","version":"blue"} <h1>API v1</h1><p>served by api-v1 (blue)</p>
2Cut over — patch the Service selector to green, all at once
No Ingress object is touched. The Ingress still points at api-svc by name — only which Pods that name resolves to has changed.
bash 
kubectl -n techmart patch svc api-svc \
  -p '{"spec":{"selector":{"app":"api","version":"green"}}}'

3Confirm every request now hits green — immediately, no partial state
bash 
for i in $(seq 1 10); do
  curl -s -H "Host: shop.techmart.local" http://localhost:8080/api
done | sort | uniq -c

4Rollback drill — flip straight back to blue
bash 
kubectl -n techmart patch svc api-svc \
  -p '{"spec":{"selector":{"app":"api","version":"blue"}}}'
✓ KEY LEARNING
  • Blue/green here costs zero Ingress edits — the indirection is entirely in the Service selector, which is why rollback is a single kubectl patch away, not a redeploy
  • Unlike canary, this is all-or-nothing per request the instant the patch applies — there's no gradual window, which is exactly the point when you need a clean rollback guarantee

Appendix

Troubleshooting checklist

Controller Pod won't start

  • kubectl -n ingress-nginx describe pod <pod> — check Events for image pull or scheduling failures
  • On a 3-node bare-metal cluster, confirm the control-plane taint isn't blocking scheduling if you expect the controller on node-1

Ingress shows no ADDRESS

  • Normal on bare metal without MetalLB — the controller Service is NodePort, not LoadBalancer, so this field is expected to stay empty
  • Use the NodePort or port-forward instead of expecting an external IP here

curl hangs, no response

  • Confirm the port-forward in Terminal 1 is still running and hasn't exited
  • Confirm ingressClassName: nginx matches your controller's actual class: kubectl get ingressclass

TLS handshake failure

  • Confirm the Secret type is kubernetes.io/tls: kubectl get secret techmart-tls -o jsonpath='{.type}'
  • Confirm the cert's CN/SAN matches the host you're connecting with — a mismatch causes verification failures, not connection failures
